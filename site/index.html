RingPilot링파일럿

검지에 끼운 반지의 IMU로 손가락 제스처를 인식해 스마트폰 화면을 넘기는 장치.

개요

문제누워서 휴대폰을 쓰려면 손을 들어 화면을 계속 만져야 하고, 이 자세가 반복되면 손목 건강에 해가 된다.
해결손을 들지 않고 내려놓은 상태에서 손가락만 움직여 화면을 스와이프한다. 검지 반지의 작은 동작(위·아래·좌우)을 인식해 화면 스와이프로 바꾸며, 위·아래는 넘기기, 좌우는 상하·좌우 모드 전환.
방식반지 보드에서 TCN 모델로 직접 판정하고 BLE로 스마트폰 앱에 결과를 보낸다. 앱은 접근성 서비스로 다른 앱에 스와이프를 넣는다.
결과개발 교차검증 정검출 97.06%, 보드 판정 14.0 ms, 실사용 시험 동작 후보 49개 중 46개 정상 발행.

한계

일상 동작 오발행

연속 동작 인식을 위해 발행 후 입력 버퍼를 초기화하면서, 일상 동작에서의 오발행이 늘었다(160회 기준 29 → 42건). 모든 움직임을 걸러내는 대신, 사용하지 않을 때는 반지 스위치로 일시정지하는 운용 방식으로 대응했다.

부품

5방향 스위치로 화면 커서 기능을 만들었으나, 스위치가 빡빡하고 각져 장시간 사용에 불편했다. 부품 자체의 한계로 기록하고 기능 코드는 유지했다.

흐름

이 페이지의 평가 지표. 발행은 모델이 50 ms 간격 슬라이딩 윈도우(1.6초)마다 내는 클래스 확률이 0.8 이상으로 2회 연속일 때 방향을 확정하는 이벤트다. 정검출은 동작 클립 하나에 정답 방향 하나만 발행된 비율(이벤트 단위 정확도)이다. 평가는 자세(posture) 5개 중 하나를 통째로 홀드아웃하는 leave-one-posture-out 교차검증으로 했다.

  1. 무선 수집으로 데이터셋 재구축

    문제 초기 데이터는 반지를 USB로 PC에 연결해 수집했다. 케이블의 무게와 장력이 손가락 동작에 섞여, 무선 사용 시와 분포가 다른 데이터가 됐다. 한 차례는 펌웨어와 앱의 자이로 스케일 설정이 어긋나 값이 절반으로 기록되기도 했다.

    조치 USB 데이터를 폐기하고, 휴대폰 앱이 소리 신호로 동작 시점을 안내하는 BLE 무선 수집 방식을 만들었다(1초 정지 후 동작, 클립당 4초). 자세 5개(앉음, 누워 팔 내림, 누워 팔 듦, 돌아누워 팔 굽힘, 돌아누워 팔 폄)로 데이터셋을 다시 구축했다.

  2. 라벨 시점과 평가 구간 재정의

    문제 첫 모델(2층 CNN)의 성공률이 10~30%대였다.

    원인 모델보다 라벨이 문제였다. 동작이 완전히 정지한 시점을 정답 시점으로 잡았는데, 손가락은 복귀 후에도 미세하게 흔들려 라벨이 실제 동작보다 크게 늦었다. 모델이 제때 예측해도 평가에서 조기 예측으로 처리됐다.

    조치·결과 정답 시점을 "복귀 동작의 자이로 피크가 절반으로 감소한 시점"으로 재정의하고 평가 구간을 다시 정했다. 같은 모델을 재평가만 했는데 9.6~35.9%가 50.7~93.9%가 됐다.

  3. 회전각 채널 정규화와 TCN 도입

    문제 "위" 동작 직후 손가락이 복귀하는 구간을 "아래" 동작으로 예측하는 반대 방향 조기 발행이 잦았다.

    시행착오 혼동 구간을 NONE 클래스의 hard negative로 추가했으나 오류가 355건에서 596건으로 늘었다. 구간을 바꿔 재시도해도 개선되지 않았다.

    원인 입력 구간과 채널을 하나씩 가리는 occlusion 분석으로 모델이 실제로 쓰는 입력을 측정했다. 모델은 직전 0.1~0.2초의 각속도 피크에 의존했고, 함께 넣은 회전각(각속도를 윈도우 안에서 적분한 값) 채널은 스케일이 작아 거의 반영되지 않았다.

    조치·결과 회전각 채널을 학습 데이터 통계로 표준화했다. 반대 방향 조기 발행이 82건에서 21건으로 줄고 정검출이 80.2%에서 91.1%로 올랐다. 모델은 수용 영역이 윈도우 전체(161샘플)를 덮는 인과 팽창 합성곱 TCN으로 교체했다.

  4. 가속도 채널 제거

    문제 학습 시간을 줄이려 일부 홀드아웃 분할로만 평가하던 동안에는 96~97%였다. 나머지 분할을 평가하자 팔을 들거나 돌아누운 자세를 홀드아웃했을 때 88%대로 떨어졌다.

    원인 자세별 중력 방향(손목 방향)을 측정하니, 손목 방향이 비슷한 자세가 학습에서 모두 빠질 때 실패가 집중됐다. 같은 동작이라도 가속도에는 중력 성분이 섞여 자세마다 분포가 크게 달랐고(코사인 유사도 −0.64~0.96), 각속도는 자세가 달라도 거의 같았다(0.78~0.99). 가속도가 처음 보는 자세로의 일반화를 방해한 것으로 판단했다.

    조치·결과 가속도 3채널을 제거하고 자이로와 회전각만 입력으로 썼다. 다섯 분할 평균 정검출이 91.98%에서 97.06%로, 미발행이 434건에서 118건으로 줄었다.

  5. 센서 읽기를 추론과 분리

    배경 학습한 모델을 C로 이식해 반지 MCU에서 온디바이스 추론하게 했다. 같은 입력에서 Python(Keras) 모델과 출력이 일치하는지 PC에서 먼저 검증했다.

    문제 추론 1회에 약 14 ms가 걸리는 동안 센서 읽기가 지연돼, 센서가 새 값을 내기 전에 같은 값을 다시 읽는 경우가 6.3% 발생했다.

    조치·결과 센서 읽기를 높은 우선순위의 FreeRTOS 태스크로 분리하고 잠금 없는 큐로 추론 루프에 넘겨 0%가 됐다. 같은 날 반지 제스처로 휴대폰 스와이프에 처음 성공했다.

  6. 좌우 제스처를 모드 전환으로 통합

    초기 설계 위·아래·왼쪽·오른쪽 4개 클래스를 각각 학습해, 움직인 방향 그대로 화면을 넘기게 했다.

    문제 실제로 써 보니 검지를 좌우로 움직일 공간이 생각보다 좁아 불편했다.

    조치 좌우 클래스는 방향을 구분하지 않고 모드 전환으로만 쓰게 했다. 상하 모드에서는 위·아래가 위·아래 스와이프이고, 좌우 모드에서는 위가 왼쪽, 아래가 오른쪽 스와이프다. 위·아래 두 동작으로 네 방향을 다룬다. 모델은 다시 학습하지 않았다.

    얻은 것과 내준 것 동작 방향과 화면 방향이 일치하는 직관성은 일부 내줬지만, 사용 편의성이 올라갔다. 좌우 간 혼동이 오류에서 빠져 정검출이 97.06%에서 97.52%가 됐다.

  7. 발행 후 입력 버퍼 초기화

    문제 동작을 빠르게 연속하면 두 번째 동작부터 인식되지 않았다.

    원인 1.6초 슬라이딩 윈도우 안에 직전 동작이 남아 있었다. 학습 데이터는 모두 "정지 후 동작" 클립이라, 직전 동작이 섞인 윈도우는 학습 분포 밖의 입력이었고 모델은 NONE으로 예측했다.

    조치·결과 재학습 대신, 발행 0.15초 뒤 윈도우의 이전 구간을 정지 상태 값으로 초기화하는 후처리를 넣었다. 빠른 반복 시험의 정답이 36%에서 100%가 됐다. 실사용 시험에서는 발행되지 않은 동작이 초기화되지 않아 다음 동작까지 연쇄로 놓치는 경우가 남아, 큰 움직임이 끝나면 발행이 없어도 초기화하도록 확장했다. 같은 실사용 기록 재생에서 동작 49개 중 정상 인식이 31개에서 46개가 됐다.

    대가 일상 동작에서의 오발행이 늘었다(160회 기준 29건에서 42건). 사용하지 않을 때는 반지 스위치로 일시정지하는 운용 방식으로 대응했다.

  8. 코드 리뷰 반영과 실기기 검증

    센서 읽기 코드 리뷰에서 센서 6축을 레지스터 단위로 따로 읽고 있고, I2C 클럭 설정도 IMU가 연결되지 않은 다른 버스에 적용되고 있음을 발견했다. 한 번의 버스트 읽기와 IMU 버스 400 kHz 설정으로 바꿔, 읽기 시간이 3.58 ms에서 0.34 ms로, 추론 시간 측정값이 21.1 ms에서 14.0 ms로 줄었다.

    앱 실기기 시험에서 앱 화면이 여러 개 생성되면 화면마다 BLE 연결을 따로 열어 제스처가 중복 실행되는 문제를 발견해, 화면을 하나로 제한했다.

    스위치 포인터 5방향 스위치로 화면 커서를 움직이는 기능을 구현했으나, 스위치가 빡빡하고 각져 장시간 사용에 불편했다. 부품의 한계로 기록했다.

# RingPilot

침대에 누워 스마트폰을 조작하기 위한 **검지 반지형 제스처 리모컨** 프로토타입이다. 반지 안 IMU로 손가락의 위·아래·좌·우 까딱임을 **반지 보드에서 직접 인식**(TinyML)하고, 휴대폰 앱이 그 결과를 화면 스와이프로 바꾼다. 쇼츠를 넘기거나 웹툰을 볼 때 팔을 들어 화면을 만지지 않아도 되는 것이 목표다.

연구·포트폴리오 목적이며 실배포 검증은 범위 밖이다. 이 문서의 수치에는 모두 측정 조건과 한계를 함께 적었다.

## 한눈에 보기

| 항목 | 내용 |
|---|---|
| 하드웨어 | Seeed XIAO nRF52840 Sense(IMU·BLE 내장), 55 mAh Li-Po, 5방향 스위치 |
| 모델 | 자이로 3 + 회전각 3채널을 받는 TCN, 4,421 파라미터, 1.6초 창, 50 ms마다 판정 |
| 보드 추론 | 판정 한 번 약 21 ms(보드 측정), 판정 p95 약 22 ms |
| 통신 | 반지 → BLE 알림 → Android 앱 → 접근성 서비스 스와이프 |
| 확인한 동작 | 유튜브·네이버 시리즈에서 스와이프 조작, 일시정지·재개 (사용자 확인) |
| 사용 방식 | 위·아래 제스처로 조작, 좌우 제스처는 상하/좌우 모드 전환 |

## 동작 구조

```text
반지(XIAO nRF52840 Sense)                                   휴대폰(Android 앱)
IMU 100 Hz → 온라인 영점 → TCN 판정(50 ms마다) → 발행 ──BLE──→ GestureRouter → 접근성 스와이프
                                                  └ LED
```

- 위·아래 제스처는 위·아래 스와이프(쇼츠 넘기기 등), 좌우 제스처는 상하·좌우 모드 전환이다. 좌우 모드에서는 위 = 왼쪽, 아래 = 오른쪽 스와이프다.
- 반지 스위치: 짧게 누르면 일시정지 해제, 0.5초 누르면 일시정지, 2초 누르면 전원 끄기.

## 설계 결정과 이유

### 1. 판정은 반지 보드에서, 폰에는 결과만 보낸다

학습 단계에서는 IMU 원시값(100 Hz 6축)을 BLE로 폰에 보내 CSV로 저장했다. 학습이 끝난 뒤에는 모델을 C로 내보내 보드에서 직접 돌린다. 반지는 "위/아래/좌/우"라는 결과만 보내므로 앱은 받은 방향을 스와이프로 바꾸기만 하면 된다. 사용자 빌드에서는 원시값 스트림 코드를 아예 꺼 두었다(`RINGPILOT_IMU_STREAM`, 기본 꺼짐). 스트림 코드는 개발 빌드용으로 `firmware/gesture_infer/src/dev/`에 남겼다.

- 스트림이 차지하는 무선 시간은 초당 약 10 ms(약 1%)로 **추정**했다. 전류 절감은 작다고 보았고, 코드 단순화를 함께 이유로 삼았다. 전력은 측정하지 않았다.
- Keras와 C 구현이 같은 결과를 내는지 PC에서 확인했다(점수 최대 오차 1e-6 수준, 연속 스트림 발행 동일).

### 2. 모델은 작은 TCN, 입력은 자이로 + 회전각

처음에는 2층 CNN(9,493 파라미터)이었다. 개선은 단계적으로 이뤄졌다.

- **회전각 채널 추가:** 자이로만으로는 "위 동작의 끝점"과 "아래 동작의 복귀"가 비슷해 보인다. 앞선 움직임의 누적(회전각)을 주면 구분에 도움이 된다.
- **TCN으로 교체:** 더 긴 과거를 보는 구조가 필요했다. 4,421 파라미터로 CNN보다 오히려 작아졌다.
- **가속도 제외:** 아래 트러블슈팅 3번에서 설명한다. 가속도에 섞인 중력이 처음 보는 자세에서 방해가 됐다.

### 3. 좌우 제스처를 "모드 전환"으로 바꿨다

네 방향을 모두 따로 인식하는 대신, 위·아래만 조작에 쓰고 좌우 제스처는 구분 없이 상하/좌우 모드를 바꾸는 버튼으로 쓴다. 좌우 모드에서는 위가 왼쪽, 아래가 오른쪽이다.

- 이유: 침대에서는 손가락을 좌우로 움직일 공간이 좁아 불편했고, 좌우 둘을 헷갈리는 오류가 사라진다.
- 대가: 손가락이 움직인 방향과 화면 방향이 항상 같다는 직관성을 일부 잃는다. 전환이 잘못 발행돼도 다시 전환하면 되돌릴 수 있으므로 감수했다.
- 입력 방식을 바꿨으니 평가 기준도 바꿨다. 같은 저장 모델을 새 규칙으로 다시 채점하자 평균에 가려진 약점(아래 방향이 가장 낮음)이 드러났다.

### 4. "항상 켜져 있되, 안 쓸 때는 끈다"는 전제

모든 일상 움직임을 걸러내려면 오발행과 놓침이 서로 교환 관계라는 문제를 풀어야 한다. 대신 쓰지 않을 때는 반지 버튼으로 **일시정지**하는 사용 방식을 전제로 두었다. 이 전제 덕분에 일상 오발행이 늘어나는 대가를 알고도 연속 동작 개선(트러블슈팅 6번)을 받아들일 수 있었다.

### 5. 연구 방식: 기준을 먼저 정하고, 한 번에 한 요인만 바꾼다

학습 전에 코드·주석·분할·선택 규칙을 고정하고 해시로 보호했다. 결과를 보고 지표를 고르지 않기 위해서다. 같은 PC와 같은 클립으로 비교하고, 뒤집힌 결정과 실패한 시도도 기록으로 남겼다.

## 트러블슈팅

자세한 표와 수치는 [시행착오 정리](docs/시행착오정리.md)에 있다. 아래는 그중 개발 방향을 바꾼 것들이다.

### 1. 점수가 낮았던 원인은 모델이 아니라 채점이었다

- **증상:** 첫 기준선의 정검출이 10~30%대였다.
- **원인 추적:** 정답 시점이 손이 완전히 멈춘 뒤의 작은 떨림까지 기다려 늦게 잡혔다. 정답 시점 앞뒤의 입력 창은 거의 같아서 모델이 구분할 수 없었다.
- **해결:** 정답을 복귀 도중의 한 시점으로 옮기고 채점 구간을 다시 정했다. 같은 모델이 9.6~35.9%에서 50.7~93.9%가 됐고 발행 지연은 약 180 ms 줄었다.
- **생각:** 점수가 낮으면 모델을 고치기 전에 자로 쓰는 정답과 지표부터 의심한다. 단, 지표를 바꿔서 오른 수치는 모델이 좋아진 것이 아니므로 구분해서 적었다.

### 2. 반대 방향 조기 발행: 틀린 가설 세 번 끝에 측정으로 찾았다

"위" 동작이 끝점에 닿는 순간을 "아래" 동작의 복귀로 착각해 반대 방향을 먼저 발행했다.

- NONE(아무것도 아님) 예시를 더하는 시도는 세 번 모두 실패했다(한 번은 355건 → 596건으로 악화).
- 추측을 멈추고, 입력의 구간과 채널을 하나씩 0으로 바꿔 판정이 어떻게 변하는지 쟀다. 모델은 최근 0.1~0.2초의 자이로 피크만 보고 **회전각은 거의 쓰지 않았다.**
- 원인은 회전각 값이 1 안팎이라 수 단위로 정규화된 자이로보다 영향력이 약했던 것이다. 회전각도 같은 방식으로 정규화하자 오류가 82 → 21건(−74%)으로 줄고 S-P5 정검출이 80.2 → 91.1%가 됐다.
- **생각:** 이번 최대 개선은 코드 몇 줄의 스케일 수정이었다. 구조를 키우기 전에 모델이 입력을 실제로 쓰는지 먼저 잰다.

### 3. 시간을 아끼려 줄인 평가가 약점을 가리고 있었다

- 10월 27일에 시간을 아끼려고 평가 분할을 두 개로 줄였다. 나머지를 돌려 보니 S-P5의 96.88%와 달리 S-P3 88.94%, S-P4 88.21%였고, S-P5는 가장 유리한 분할이었다.
- 무발행이 특정 검증 세션에 몰렸다. 세션별 손목 방향(중력 방향)을 재 보니 P1–P2가 약 20°, P3–P4가 약 59°로 짝을 이뤘고, 짝이 학습에서 함께 빠지면 무발행이 급증했다. 같은 동작의 회전은 세션 간에 거의 같았지만 가속도 변화는 크게 달랐다.
- 가속도 3채널을 뺐다. S 평균 91.98 → 97.06%, 무발행 합 434 → 118건. 중력만 뺀 가속도를 다시 넣어 봤지만(95.95%) 채택하지 않았다.
- **생각:** 평가 분할을 줄이는 결정은 시간만 아니라 볼 수 있는 약점도 줄인다. 입력을 더 넣는 것이 늘 좋지는 않다.
- 이 값들은 모두 개발용 교차검증이며 실제 사용 성능이 아니다.

### 4. 데이터를 빼고 성능을 비교하다 속을 뻔했다

약한 동작 14개를 학습·평가에서 제외하자 수치가 오른 듯 보였다. 그러나 이전 모델을 남은 클립으로만 다시 채점해도 같은 수치가 나왔다. 오른 것은 모델이 아니라 어려운 클립이 빠진 효과였다. 이후 약한 동작도 조작으로 받는 쪽(피로 감소)으로 정하고, 데이터를 빼는 비교는 같은 클립으로 다시 채점하게 했다. 같은 seed라도 PC가 다르면 최대 5.5%p 차이가 나서 기준선은 같은 PC에서 다시 만들었다.

### 5. 사전 기준이 제품 의도와 어긋난 적이 있었다

속도 증강은 정검출을 올렸지만 배경 오발행이 늘어, 결과 전에 정한 기준 때문에 처음에는 채택하지 않았다. 이후 "약한 동작도 받는다"는 우선순위를 정하면서 뒤늦게 채택했다. 사전 기준은 결과를 보고 고르는 일을 막아 주지만, 기준이 우선순위를 반영하지 못하면 절차가 맞아도 답이 틀린다. 기준을 바꿀 때는 이유를 기록했다.

### 6. 연속 동작이 안 먹었다 — 재학습 없이 입력 처리로 풀었다

바로 이어서 동작하면 인식되지 않았다. 33초 연속 기록을 재생해 보니 모델 점수가 낮았고, 앞 동작이 판정 창에 남아 영향을 주는 것으로 좁혀졌다.

- 앞 동작을 섞어 학습하는 방법은 빠른 반복을 늘렸지만 단일 동작 성능이 떨어지고 배경 오발행이 3~4배가 되어 보류했다.
- 대신 발행 150 ms 뒤에 입력 이력을 정지 값으로 지우고, 발행 없이 끝난 큰 움직임도 지우도록 보드 코드를 바꿨다. 같은 33초 기록의 빠른 위 동작이 36 → 100/100이 됐다(같은 동작 5개를 모델 20개로 재생한 합이라 독립된 100회가 아니다).
- 대가도 있다. 일상 동작 발행이 늘어 사전 기준에는 미달이었다. 이를 알고 보드에 올렸고, 쓰지 않을 때 일시정지하는 사용법으로 부담을 줄였다.
- 실사용 기록에서 동작 후보 49개 중 46개가 정상 발행됐다(아래 "확인한 것" 참고).
- **생각:** 비싼 재학습보다 작은 입력 처리가 효과적이었다. 이득과 대가를 둘 다 기록하고 알고 선택했다.

### 7. 하드웨어·데이터 쪽에서 겪은 일

- **USB 수집 데이터 폐기:** 케이블의 무게와 당김이 동작에 섞여 무선 사용을 대표하지 못한다고 판단해 BLE 수집으로 바꿨다.
- **펌웨어와 앱의 자이로 범위 불일치:** 펌웨어는 ±2000 dps인데 앱이 ±1000 dps로 환산해 자이로가 절반으로 기록됐을 가능성이 있었다. 펌웨어를 올릴 때 앱 버전과의 짝을 확인하지 않은 것이 원인이다. 그 세션들을 폐기하고 앱을 맞춘 뒤 자세별 5세션을 다시 수집했다. 이후 `gyro_range_dps=2000`을 기록에 남긴다.
- **충전 중 자동 기동:** nRF52840은 USB 전원이 들어오면 System OFF에서 깨어난다. 꺼 둔 채 충전해도 펌웨어가 동작하므로 켜져 있는 동안 `VBAT_ENABLE`(P0.14)을 LOW로 두게 했다.
- **연구 도구 쪽:** PC 대기 모드로 긴 학습이 1시간 40분 멈춘 뒤 대기를 막는 래퍼를 썼고, 학습을 너무 많이 병렬로 돌려 메모리가 부족해지면 병렬 수를 줄였다.
- **제스처 알림 유실 가능성:** 코드 리뷰 중 IMU 스트림으로 BLE 송신 버퍼가 찬 순간 발행이 나오면 제스처 알림이 사라질 수 있음을 발견했다. 실제 기록에서 드러난 적은 없다. 알림 대기열(4개)과 재전송을 넣었고, 사용자 빌드는 스트림을 꺼서 가능성 자체를 줄였다.

## 성능이 바뀐 흐름 (개발용 교차검증)

정검출은 클립 안에 정답 방향 발행이 있고 다른 방향 발행이 없는 비율이다(seed 5개 평균). **실제 연속 사용 성능이 아니다.**

| 단계 | 바꾼 것 | S-P5 |
|---|---|---:|
| 채점 변경 | 채점 구간을 복귀 피크~r+500으로 | 63.3% |
| 입력 추가 | 회전각 3채널 | 70.2% |
| 모델 변경 | TCN | 80.2% |
| 스케일 수정 | 회전각 정규화 | 91.1% |
| 증강 | 회전 사본, 속도 변형 | 95.3% |
| 입력 제거 | 가속도 3채널 제외 | 96.7% |

처음 기준선의 34.4%는 지표와 채점 구간이 달라 이 표와 직접 비교할 수 없다. S-P5는 가장 유리한 분할이고, 다섯 S 분할 평균으로 보면 가속도를 뺀 뒤 91.98% → 97.06%다.

## 확인한 것과 한계

**확인한 것**
- 오프라인: 세션(자세)을 나눈 교차검증에서 단일 동작 정검출 평균 약 97%(클립 단위).
- Python과 C: 같은 입력에서 점수 최대 오차 1e-6 수준, 연속 스트림 발행 동일(`ml/v2_export_c.py check`).
- 보드: 판정 약 21 ms, 실제 동작 중 판정 18,078회에서 센서 재읽기 0회(2026-10-31 측정).
- 실사용(사용자 1명, 약 1~2분 기록 2회): 두 번째 시험에서 동작 후보 49개 중 46개 정상 발행, 체감 "끊김 없이 잘 됨". [field-02](docs/experiments/ble-v2/field-02/README.md).

**한계 (측정하지 않았거나 주장하지 않는 것)**
- 독립 평가가 없다. 클립 334개가 모두 개발에 쓰였다.
- 연속 인식률과 시간당 오발행을 측정하지 않았다. 명령이 아닌 움직임에서의 오발행은 일부러 헷갈리게 모은 자료에서 클립당 0.202건이었다.
- 동작부터 화면 반응까지의 지연은 체감만 있고 수치가 없다. 배터리 지속 시간, BLE 최대 거리, 소비 전류도 재지 않았다.
- 시작 간격 약 0.55초의 빠른 동작, 전환 직후 조작, 다른 앱을 오래 쓰며 연결이 유지되는지는 확인하지 못했다.
- 사용자 한 명, 한 날의 자세 5개 세션 자료라 일반화 범위가 좁다.
- 2026-11-05의 구조 정리(펌웨어·앱 모듈 분리, 제스처 알림 재전송, IMU 스트림 끄기, 개발 코드 분리)는 컴파일·빌드와 PC 테스트까지만 확인했다. 새 펌웨어를 보드에, 새 앱을 폰에 올려 동작을 확인하지 않았다.

## 실행

1. [설치 안내](docs/설치안내.md)에 따라 Arduino·Python·Android 빌드 환경을 준비한다(`setup.ps1`).
2. [펌웨어 안내](firmware/README.md)대로 `firmware/gesture_infer`를 반지에 올린다.
3. [앱 안내](android/README.md)대로 APK를 빌드·설치하고, `RingPilot-IMU`를 페어링한 뒤 앱에서 스와이프 제어를 켠다.
4. 모델을 다시 학습하거나 평가할 때는 `ml/v2_return.py`(학습·채점), `ml/v2_export_c.py`(C 헤더 내보내기·일치 확인)를 쓴다. 테스트는 `ml/.venv/Scripts/python.exe -m unittest discover -s ml`.

개발용 화면(수집·기록 탭)이 필요하면 `-PdevTools=true`로 앱을 빌드한다. 자세한 내용은 [앱 안내](android/README.md)에 있다.

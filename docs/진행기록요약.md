# RingPilot 진행기록 요약

[진행기록](진행기록.md)(2026-09-14~11-16, 작업 항목 약 280개)을 단계별로 간추린 문서다. 원본은 작업마다 목적·조건·수치·문제를 모두 남긴 일지라 그대로 보존하고, 이 문서는 흐름과 결과만 담는다. 수치의 측정 조건과 근거는 원본과 각 실험 README에 있다.

기준일: 2026-11-17

- **정검출**: 동작 클립 안에서 정답 방향 명령이 나오고 다른 방향 명령은 나오지 않은 비율.
- **분할**: S-P1~S-P5는 수집 세션(P1~P5) 하나를 통째로 검증에 쓰는 교차검증, C는 클립을 세션 구분 없이 나눈 교차검증이다. 모든 PC 수치는 개발용 교차검증 값이며 실제 사용 성능이 아니다.
- **사용자 확인**: 보드·앱의 실제 동작은 사람이 직접 보고 확인한 경우에만 확인으로 적었다.

## 단계별 요약

### 1. 하드웨어·통신 확인 (09-14~09-22)

- 보드는 Seeed XIAO nRF52840 Sense, 개발 환경은 Arduino(Seeed nRF52 코어 1.1.13, non-mbed)로 정했다.
- Galaxy S10(Android 12)과 BLE HID로 페어링해 포인터 4방향 이동과 클릭을 확인했다. Custom GATT 알림과 HID를 동시에 쓰고, USB 재연결·폰 블루투스 재시작 뒤에도 복구되는 것을 확인했다(사용자 확인).
- Android 앱의 접근성 서비스로 화면 스와이프를 내보내는 경로를 만들고 상하좌우 모두 확인했다.
- 업로드 포트가 사라지는 문제는 RST로 부트로더에 진입해 복구했다.

### 2. 첫 데이터와 모델 (09-28~10-06)

- Edge Impulse와 USB 연결로 IMU 6축 100 Hz를 수집했다. 방향별 원시 제스처를 모으고 손이 제자리로 돌아온 완료 시점을 주석으로 달았다.
- 800·1200·1600 ms 인과(causal) 창을 비교해 800 ms를 제외하고 1600 ms를 기본으로 정했다.
- 회전·노이즈 증강으로 데이터를 5배로 늘려 Edge Impulse Studio에서 Dense·1D CNN을 학습했다.
- 이 단계의 데이터와 결과는 3단계에서 폐기해 현재 성능과 비교할 수 없다.

### 3. 반지 하드웨어와 무선 수집 (10-18~10-23)

- 5방향 스위치(SKRHACE010, 공통 GND), 55 mAh 배터리 단독 구동, 센터 길게 누름으로 System OFF와 재기동을 확인했다. 상세는 [하드웨어 제작 보고서](HardwareBuild.md).
- IMU 6축을 BLE로 보내는 펌웨어와 폰 수집 앱(녹화 4초·대기 1초 안내, 원시값 CSV 저장, PC로 옮기는 도구)을 만들었다. 일시정지와 System OFF를 분리하고 재연결 버그 3건을 고쳤다.
- **USB 데이터 폐기:** 케이블의 무게와 당김이 동작에 섞여 무선 사용을 대표하지 못한다고 판단했다. 학습도 Edge Impulse에서 로컬 Python(TensorFlow)으로 옮겼다.
- 무선 데이터로 BLE v1 실험 1~7a(클래스 가중치, 라벨 폭, 입력 길이, Flatten/GAP)를 진행했다. 데이터가 적어 이후 코드 동작 확인용으로 다시 분류했다. 상세는 [조현준 실험 기록](진행기록_조현준.md).
- **데이터 삭제:** 펌웨어(자이로 ±2000 dps)와 앱 환산(±1000 dps)이 어긋난 것을 발견해 기존 세션을 모두 삭제했다. 펌웨어를 바꿀 때 앱 버전과의 짝을 확인하지 않은 것이 원인이다.

### 4. 재수집과 기준선 (10-25)

- 자세를 달리한 5세션(P1~P5)을 다시 모았다. 방향 클립 296개와 배경 클립 40개(정지 15, 명령이 아닌 움직임 25)다. 이후 라벨이 잘못된 클립 2개를 빼 334개가 됐다.
- 평가 방식(S-P1~S-P5, C 분할, seed 5개)과 학습 절차를 결과 전에 고정했다.
- 기준선(2층 CNN, 손이 완전히 멈춘 시점을 정답으로) 정검출은 9.6~34.4%였다. 기준선과 배경 배분 비교에 보정 학습 250회를 썼다.
- 이 시점까지의 회고는 [개발 진행 요약](archive/개발진행요약_2026-10-25.md).

### 5. 모델 개선 (10-26~10-29)

시도 순서대로 정검출이 바뀐 흐름이다(seed 5개 평균). 자세한 원인과 실패한 시도는 [시행착오 정리](시행착오정리.md).

| 바꾼 것 | C | S-P5 |
|---|---:|---:|
| 기준선(옛 지표) | 17.8% | 34.4% |
| 채점 구간을 실제 명령 시점에 맞춤 | 79.4% | 63.3% |
| 정답 시점을 복귀 도중으로 | 74.0% | 68.5% |
| 회전각 3채널 추가 | 84.3% | 70.2% |
| TCN으로 변경 | 91.0% | 80.2% |
| 회전각 채널 정규화 | 95.9% | 91.1% |
| 실시간 영점 | 95.6% | 90.0% |
| 회전 증강 | 98.4% | 94.0% |
| 속도 증강 | 98.4% | 95.3% |
| 채점 구간 조정 | 98.6% | 96.9% |
| 가속도 3채널 제거 | 98.3% | 96.7% |

- **가장 큰 개선은 측정에서 나왔다.** 입력 구간·채널을 하나씩 가려 보니 모델이 회전각을 거의 쓰지 않았다. 값의 크기가 작았던 탓이라 정규화만으로 S-P5가 80.2 → 91.1%가 됐다.
- **가속도 제거의 효과는 S-P5만으로는 보이지 않았다.** 시간을 아끼려 줄였던 나머지 분할을 돌리자 S-P3·S-P4가 89% 안팎이었다. 세션 간 손목 방향 차이로 가속도에 섞인 중력이 원인이었고, 가속도를 빼자 S 평균이 91.98 → 97.06%가 됐다.
- 배경 클립 오발행을 줄이려 넣은 끝점 근처 NONE 추가, 발행 문턱 0.7, 부드러운 라벨, 연속 3회 규칙은 정검출을 떨어뜨리거나 오류 종류만 바꿔 채택하지 않았다.

### 6. 보드 탑재 (10-31)

- TCN을 C로 옮기면서 마지막 판정에 필요한 위치만 계산하게 했다(블록별 93·45·21·9·3·1칸). PC 실행 결과 Keras 대비 점수 최대 오차는 5.1e-7, 발행 시각·방향 차이는 0건이었다.
- 첫 보드 측정에서 판정 중앙값 14.09 ms, 센서 재읽기 6.3%가 나왔다. 센서 읽기를 FreeRTOS 태스크로 분리해 재읽기를 0/6,017로 없앴다.
- 334개 클립 전체로 학습한 모델(TCN, 회전·속도 증강, 가속도 제거)을 보드에 올렸다.
- 반지 제스처로 유튜브와 네이버 시리즈의 상하좌우 스와이프에 처음 성공했다(사용자 확인).

### 7. 연속 사용 (10-31~11-04)

- **문제:** 동작을 바로 이어 하면 인식이 안 됐다(약 0.53초 간격 위 5번 중 1번 발행).
- **원인:** 33초 연속 기록을 입력을 바꿔 가며 재생해 보니, 판정 창에 남은 앞 동작 파형이 원인이었다.
- 앞 동작을 붙인 합성 학습은 단일 동작 정검출이 떨어지고 일상 동작 오발행이 3~4배가 돼 보류했다.
- **좌우 제스처를 모드 전환으로 통합(11-02):** 좌우로 움직일 공간이 좁다는 피드백을 반영했다. 위·아래로만 조작하고 좌우 동작은 상하·좌우 모드를 바꾼다.
- **발행 후 입력 버퍼 초기화:** 명령을 낸 150 ms 뒤 입력 이력을 비웠다. 재학습 없이 빠른 연속 동작 정답이 36 → 100/100, 편한 간격 오답이 0이 됐다. 대신 일상 동작 오발행이 늘어(160회 기준 29 → 42, 19 → 36) 결과 전에 정한 기준에는 미달했으나, 쓰지 않을 때 일시정지하는 사용법을 전제로 채택했다.
- **명령 없이 끝난 움직임도 초기화:** 실사용 기록 2회(한 사람, 약 130초·66초)에서 놓친 동작을 분석해 추가했다. 두 번째 기록의 동작 후보 49개 중 46개가 정상 발행됐다(이전 규칙으로 재생하면 31개). 상세는 [field-01](experiments/ble-v2/field-01/README.md), [field-02](experiments/ble-v2/field-02/README.md).

### 8. 앱 정리와 코드 리뷰 (11-05~11-12)

- 앱 화면을 다시 디자인하고, 리모컨 화면을 스크롤 없이 한 화면에 맞췄다. 수집·기록 같은 개발용 화면은 코드를 남긴 채 빌드 옵션(`-PdevTools=true`)으로만 켜지게 했다.
- 펌웨어와 앱을 기능별 파일로 나누고, 개발용 코드는 `dev/` 폴더로 분리했다. 초기 하드웨어 시험 스케치는 삭제했다.
- 코드 리뷰 중 발견해 고친 것: 제스처 알림 전송 실패 시 재전송, 사용자 빌드에서 IMU 스트림 끄기, 샘플이 올 때 loop를 깨우는 방식, IMU 몰아 읽기와 I2C 400 kHz, 사용자 빌드에서 가속도 끄기.
- 별도 리뷰(11-12)에서 지적된 8건(수집 중 상태 충돌, 같은 초 세션 폴더 덮어쓰기, 펌웨어 대기열 동시 접근, 학습 결과 누락 시 빈 요약 저장 등)을 수정했다. Java 검사 274개, Python 테스트 90개 통과.
- 5방향 스위치로 커서를 움직이는 포인터를 만들었다. BLE 마우스(HID)로 시작했다가, 커서를 평소 숨기려고 앱이 커서를 그리는 방식으로 바꿨다.

### 9. 실기기 재확인 (11-16)

- 실사용 기록의 실시간 영점이 학습 데이터의 영점 범위 안에 있어(시간의 98.5%, 100%) 영점 방식은 바꾸지 않았다. 상세는 [bias-01](experiments/ble-v2/bias-01/README.md).
- I2C 400 kHz가 IMU가 연결된 버스(`Wire1`)가 아닌 다른 버스에 설정된 오류를 찾아 고쳤다. 판정 중앙값 21.1 → 13.95 ms, 센서 읽기 평균 336 µs, 초당 판정 20회.
- 스위치 방향 매핑(위 D6, 아래 D0, 왼쪽 D3, 오른쪽 D2)과 전원 끄기를 확인했다(사용자 확인).
- 포인터는 동작하지만 스위치가 빡빡하고 머리가 각져 오래 밀기 어려워, 실사용에 맞지 않는 부품의 한계로 판단했다. 코드는 남겼다.
- 앱 화면이 여러 개 쌓이면 화면마다 반지에 연결해 제스처가 중복 실행되는 문제를 찾아, 화면을 하나만 두도록 고치고 재확인했다(사용자 확인).

## 현재 상태

**확인된 것**

- 반지 단독 추론 → BLE → 앱 → 스와이프로 유튜브·네이버 시리즈를 조작한다. 일시정지·재개, 모드 전환, 전원 끄기 포함(사용자 확인).
- 보드 판정 중앙값 13.95 ms, 초당 20회 판정(USB 연결, 정지 상태 측정).
- PC 교차검증 정검출: S 평균 97.06%, 주로 쓰는 위·아래는 S-P3·S-P5에서 96.1%·96.9%.

**확인하지 못한 것**

- 독립 평가: 334개 클립이 모두 개발에 쓰여 따로 남긴 시험 데이터가 없다.
- 연속 사용 인식률과 시간당 오발행: 실사용 기록 2회와 체감뿐이다.
- 일상 동작 오발행: 명령이 아닌 움직임 클립당 약 0.2건으로, 가장 큰 남은 위험이다.
- 동작부터 화면 반응까지의 지연, 배터리 사용 시간, 연결 거리.

# RingPilot 제스처 인식 구조 제안 v2

2026-09-28. 사용자가 기존 문서의 제약을 재검토하도록 요청한 뒤 작성한 설계 제안. 실측으로 최적성이 입증된 구조 또는 구현 완료 사양이 아니다.

> **2026-10-23:** 학습·주석은 로컬(`ml/`, `tools/suggest-gesture-completions.js --local-dir`)에서만 한다. 이 문서의 표본 수·비교 결과는 삭제된 이전 데이터 기준이며, 현재 저장소에는 학습용 데이터가 없다.

## 권고

연속 6축 IMU → 과거 맥락 버퍼 → 현재 시점의 제스처 완료를 판단하는 작은 causal temporal CNN → 출력 펄스 중복 제거 → BLE GestureEvent.

모델 질문을 '이 창 안에 어떤 동작이 있는가'에서 '최근 짧은 시간 안에 어느 방향의 새 제스처가 완료됐는가'로 바꾼다. 관찰 맥락 길이와 양성 출력 지속시간을 분리하는 것이 핵심이다. 초기에는 자연 복귀 완료를 이벤트 기준으로 삼는다.

## 첫 실험값과 의미

| 항목 | 후보 | 의미 |
|---|---|---|
| 센싱 | 현재 100 Hz, accel+gyro 6축 | 실제 간격과 누락 확인 필요 |
| 과거 입력 길이 L | 1600 ms | 1차 진단에서 800 ms 제외, 1200 ms를 비교군으로 유지 |
| 추론 stride S | 50 ms | 5개 새 센서 시점마다 판정 |
| 양성 출력 구간 B | 완료 후 150 ms | 100/150/200 ms 비교 후보 |
| 모델 출력 | RIGHT/LEFT/UP/DOWN/NONE | NONE은 '새 이벤트 없음' |
| 이벤트 확정 | 같은 방향 2회 연속 점수 조건 통과 | 최초 실험값, 50 ms 추가 확인 |
| 출력 재무장 | 확실한 NONE 2회 연속 | 물리적 정지와 다름 |

L, B, S, 확인 횟수는 함께 튜닝한다. L은 지원할 제스처의 판별 맥락 길이와 양성 구간 말미까지의 여유를 포함해야 한다. 시작 맥락까지 필요한 동작 길이를 D라 하면 L≥D+B를 초기 보수 조건으로 점검한다. 1600 ms보다 긴 동작을 자동으로 지원한다고 가정하지 않는다.

100 Hz의 1.6초 6축 float32 원시 버퍼는 160×6×4=3840 bytes다. 1.2초 입력은 2880 bytes이므로 차이는 960 bytes다. 버퍼 복사, 모델 activation, tensor arena, BLE 메모리는 별도다. 버퍼가 작다고 MCU 추론 가능성을 확정하지 않는다.

## 입력 길이 1차 진단 결과

AUTO 30개를 원본 샘플 단위로 분리한 5-fold 교차검증에서 800/1200/1600 ms를 같은 선형 진단 모델로 비교했다. 800 ms는 완료 직후 양성 window가 주동작 시작까지 포함한 샘플이 6/30뿐이어서 주 후보에서 제외했다. 1200 ms는 이벤트 검출이 12/30으로 가장 높았고, 1600 ms는 맥락 포함이 28/30, NONE window 오검출이 19.97%, 방향 macro F1이 0.2718로 세 후보 중 가장 나았다.

그러나 최고 이벤트 검출도 40%이고 모든 길이에서 3초 clip당 목표 밖 이벤트가 1회를 넘었다. 이는 최종 모델 성능이 아니라 후보 제거용 결과다. 다음 causal CNN/TCN은 1600 ms를 기본으로 하고 1200 ms를 비교군으로 유지한다. 당시의 세부 문서(`WindowLengthComparison.md`)는 USB 데이터 삭제와 함께 2026-10-21에 정리했다.

## 학습 라벨의 계약

- 연속 원본에서 방향, 출발, 반환 전환점, 자연 복귀 완료 e, 이벤트 ID, 세션 ID, 착용 조건을 주석으로 보존한다.
- 시각 t의 입력은 과거 전용 x[t-L,t]이다. 미래 데이터는 포함하지 않는다.
- 최근 완료 이벤트의 방향이 c이고 0≤t-e<B이면 c, 그렇지 않으면 NONE을 목표로 한다. 관측 맥락이 부족하거나 주석이 불확실한 사례는 명시적으로 검토한다.
- 오래된 RIGHT가 버퍼 안에 남아 있어도 e+B 이후 목표는 NONE이다. 대기 상태뿐 아니라 출발·진행 중·완료 후 오래된 맥락에도 NONE 목표가 가능하다.
- 두 완료 이벤트가 B 이내에 발생하면 목표 펄스가 충돌한다. 지원 최소 이벤트 간격을 검증하고 이런 기록을 따로 평가한다. 임의로 같은 사건으로 합치지 않는다.
- 완료 직전/직후의 주석 오차를 측정한다. 필요하면 작은 경계 완충 구간을 loss에서 제외하거나 부드러운 목표를 비교하되, 평가 스트림에서는 제거하지 않는다.
- 준비·복귀 데이터를 잘라 버리지 않는다. 원본 세션을 먼저 train/validation/test로 나누고 동일 시간 격자로 window를 만든다.
- 시간 이동 증강은 이벤트 주석도 함께 이동한다. 이벤트가 입력 안에 있다는 이유만으로 모든 위치에 방향 라벨을 주지 않는다.
- 실제 배경 맥락, 이전 명령, 빠른/느린 왕복, 지연 복귀, 미완료/취소 동작을 포함한다. 합성 왕복과 과도한 시간 압축을 초기 데이터의 대체물로 사용하지 않는다.
- idle/other는 NONE 원본으로 재사용하되 하위 종류를 보존한다. 기존 데이터의 파형·착용 품질은 별도 확인 대상이다.

### 현재 완료 시점 주석 기준

사용자는 방향 이동 뒤 자연 복귀가 끝난 시점을 이벤트 완료로 사용하기로 결정했다. 초기 자동 후보는 전체 자이로 동작 에너지의 99%가 지난 뒤, 최종 자세 부근에서 IMU가 180 ms 안정되기 시작하는 첫 시점으로 계산한다. 끝점에서 잠깐 멈췄다가 복귀하는 동작을 완료로 오인하지 않기 위해 99% 에너지 시점 전에는 안정 구간을 찾지 않는다.

`tools/suggest-gesture-completions.js --local-dir`가 세션 폴더의 `raw_*` 파일을 읽어 후보를 계산하고, 결과는 `data/annotations/`에 둔다. 검토 표시(`REVIEW`) 샘플은 삭제하지 않지만 첫 모델의 기본 학습에서는 제외하고 어려운 사례 평가에 사용한다.

이 자동 시점은 실측 이벤트 정답을 완전히 대신하지 않는다. 최초 모델과 연속 replay 결과를 확인한 뒤 경계 오차, 안정 시간 180 ms, 양성 폭 150 ms를 조정한다.

## 모델

작은 causal 1D CNN/TCN을 우선한다. 시간 순서와 축 부호를 보존하고 최종 시점의 특징으로 현재 이벤트를 예측한다. global average pooling만으로 전체 시간축을 뭉개는 기본 분류기를 그대로 쓰지 않는다. 마지막 시점의 receptive field가 필요한 맥락을 실제로 덮는지 확인한다.

TCN의 causal convolution은 미래를 참조하지 않는 시간 처리 방식이다. 고정 과거 창 전체를 CNN으로 처리하는 구현도 외부 입력 기준으로 causal하게 만들 수 있다. TCN만이 유일한 해법이거나 이 보드에서 가장 빠르다고 주장하지 않는다.

초기에는 숨은 상태를 영구 유지하지 않고 매번 명시적인 유한 과거 버퍼를 처리한다. PC replay와 MCU 결과 일치, 부팅·누락 후 복구를 확인하기 쉽기 때문이다. 추론 비용이 실제로 크면 캐시된 convolution이나 작은 GRU를 비교하되, recurrent 상태가 세션 분리와 reset에 미치는 영향을 검증한다.

int8 변환 및 실제 보드 컴파일을 작은 모델부터 조기에 시험한다. dilation/causal padding 등 연산 지원과 scratch 메모리를 확인하며, 미지원이면 배포 가능한 일반 convolution 구조로 바꾼다.

축별 스케일은 훈련 세션에서 계산한 값으로 고정하고 MCU에서도 일치시킨다. gyro 정지 편향과 반지 장착 방향을 점검한다. 정지 여부를 동작 인식 게이트로 사용하지 않는다. 화면 좌표와 손/반지 좌표의 의미는 데이터 수집 전에 명시한다.

## 출력 후처리

- 같은 방향의 충분한 점수/경쟁 클래스 차이를 연속 확인한 첫 시점에 1회 전송한다.
- 전송 후에도 모든 window를 계속 추론한다. 확실한 NONE이 연속 확인될 때 출력만 재무장한다.
- 약한 방향 점수를 NONE 확신으로 자동 간주하지 않는다. 후보 방향이 바뀌면 확인 수를 초기화한다.
- 긴 고정 cooldown, 물리적 정지 복귀 조건, timeout에 의한 주기적 재발행은 기본값으로 넣지 않는다.
- 펄스가 둘로 쪼개지거나 두 제스처 펄스가 이어지는 문제는 여전히 가능하다. 중복률과 빠른 연속 명령 누락률을 함께 측정한다.
- 이벤트 펄스가 150 ms이고 stride가 50 ms여도 모델 출력이 이상적이라는 보장은 없다. 연속 확인 횟수는 실제 점수 시퀀스로 조정한다.
- 향후 BLE 패킷에 session/event sequence를 넣어 앱에서도 같은 전송 이벤트를 중복 실행하지 않게 할 수 있다. 이는 모델이 중복 생성한 서로 다른 이벤트를 해결하지 못한다.

## 반응성과 실패 한계

1.2초는 매번 기다리는 시간이 아니라 유지하는 과거다. 초기 buffer warm-up 후 50 ms마다 갱신한다. 완료 후 즉시 펄스가 안정적으로 발생한다면 위상 대기 0~50 ms와 추가 확인 50 ms, 계산/통신 시간이 더해진다. 이 수치는 구조상 대기 항목이며 실측 지연 보장이 아니다. 출발부터의 지연에는 왕복 자체의 시간이 포함된다.

자연 복귀가 너무 느려 사용감이 나쁘면 같은 자료에서 외향 동작 완료 기준의 조기 이벤트 모델을 별도로 비교한다. 장기 과거 맥락은 유지하되 지연 복귀의 반대 명령 오인식을 다시 검증한다. 과거 정보가 없는 독립 창으로 조기 실행과 임의의 긴 복귀 지연을 모두 해결한다고 가정하지 않는다.

센서상 같은 궤적을 명령/비명령 의도로 각각 수행하는 경우 어떤 IMU 모델도 의도를 확정할 수 없다. 일상 동작과 충분히 구별되는 제스처 형태, 재현 가능한 장착과 좌표 정의가 필요하다. FP 목표를 달성하지 못하면 무조건 모델 크기를 늘리기보다 제스처 모양 또는 명시적 활성화 UX를 검토한다. 추가 입력은 현재 채택한 사양이 아니다.

## 대안 비교 및 선택 이유

| 구조 | 판단 |
|---|---|
| 400 ms 창 전체의 행동 분류 | 비교 기준으로 유지. 장기 복귀 맥락과 이벤트 시점 표현에 한계 |
| motion gate 후 이벤트 crop | 경계 규칙과 느린 복귀의 오류를 추가하므로 현재 추천에서 제외 |
| 길어진 창 전체 행동 분류 | 맥락은 늘지만 이전 제스처가 남아 지속 검출되는 문제를 라벨에서 해결하지 못함 |
| 장기 맥락 + 현재 이벤트 모델 | 우선 제안. 맥락 길이와 이벤트 출력 폭을 분리하되 시점 주석 비용 증가 |
| GRU 등 상태 유지 모델 | 연산/성능 비교의 후속 후보. reset 및 상태 전파 검증 필요 |
| 단계별 다중 head/CTC/Transformer | 첫 단계에는 학습·배포 복잡성 증가. 필요성을 입증한 뒤 검토 |

## 구현 순서와 통과 조건

1. 원시 연속 데이터와 시점 주석 도구. 타임스탬프·순번·축 단위·세션/착용 조건 보존. 2초 단일 라벨 파일 반복만으로 대체하지 않는다.
2. 방향별 20~30회 규모로 자연 왕복과 복귀 지연을 관측. 정밀도 주장보다 지원 시간 범위와 좌표/제스처 정의 검증이 목적.
3. 1차 선형 진단에서 제외한 800 ms를 되살리지 않고, 같은 분할의 causal CNN/TCN으로 1200/1600 ms 이벤트 모델을 비교한다. validation에서 threshold/B/debounce를 선택하고 test를 재튜닝에 쓰지 않는다.
4. 연속 replay에서 시작 위상, RIGHT→RIGHT/LEFT, UP→DOWN, 지연 복귀, 부분 동작, 스틱 조작, 재착용을 검증. 이벤트 일대일 매칭으로 recall/방향 오류/복귀 오발행/중복/FP-hour/최소 반복 간격/지연 median-p95를 보고한다.
5. 가장 작은 배포 가능 모델을 XIAO에 조기 빌드하고 실제 전처리+추론 시간·메모리를 측정. 완성된 학습 결과를 기다렸다가 포팅 위험을 발견하지 않는다.
6. 샘플링 태스크/FIFO와 추론을 분리하고 BLE까지 켠 조건에서 누락·jitter·전력·end-to-end 지연을 측정한다.

학습·window 생성·연속 replay는 로컬 Python(`ml/`)에서 관리한다. 준비한 고정 창을 그대로 쓰도록 입력 길이를 맞추고, 보드 배포 시 변환(int8 등) 호환성은 실제 구현 시 검증한다.

현재 완료 시점 주석과 선형 진단 기준선까지 구현했다. 800 ms는 주 후보에서 제외했지만 1200/1600 ms 중 최종값, 실제 causal CNN/TCN의 인식률, FP/hour, MCU 추론 시간은 아직 미검증이다.

## 근거와 해석

- TCN의 일반적인 시퀀스 모델링 근거: https://arxiv.org/abs/1803.01271 . RingPilot 성능이나 MCU 우월성을 입증하는 연구로 해석하지 않는다.
- 보드 추론이 blocking으로 동작하면 연속 센싱과의 병행을 별도로 설계한다.
- 시간 구간을 입력 맥락과 event-time 목표로 분리하는 구체적인 라벨/후처리 구성은 본 프로젝트를 위한 제안이다.

## 1. 결론

| 질문 | 판정 |
|---|---|
| 현재 코드 그대로 4초 가이드 클립의 CSV와 영상을 ≤50 ms로 대응시킬 수 있는가 | **아니오.** CSV에는 호출 시각·첫 슬롯 번호가 없고(§2), 앱 비프·화면 신호로는 CSV 0 ms를 최소 약 100 ms 폭으로밖에 못 정한다(§3, §4-c). |

| 권장 경로 | **앱이 캡처마다 첫 슬롯 번호를 sidecar에 저장**(앱 소폭 변경) + 연속 기록으로 감싼 탭 표식 + 60 fps 이상 영상. 보드는 부팅 이후 10 ms 슬롯 번호를 세므로, 같은 부팅 안에서는 표식 한 쌍으로 모든 클립을 영상에 대응시킬 수 있다. 펌웨어 LED 표식(§4-b)은 선택 보강이다. |

### CSV 시각 규칙성 (읽기 전용 계산, 스크래치 스크립트)

`data/sessions` 5세션 CSV 336개(가이드 296개 × 400행, idle/other 40개 × 1000행)를 전부 읽었다. 첫 `timestamp`는 336개 모두 0이고, 인접 간격이 10 ms가 아닌 경우는 0건이다. 의미: 저장 자료의 시간축은 샘플 번호이고 도착 지터·재전송이 흔적을 남기지 않는다. 반대로 "CSV 0 ms가 실제로 언제인가"는 CSV로 알 수 없다. 기존 클립의 촬영 당시 휴대폰 시각은 복원할 수 없다.

## 3. BLE 배칭이 만드는 CSV 0 ms의 불확실성 (모델 추정)

가정: 10샘플 묶음이 약 100 ms 주기로 안정적으로 도착하고, 송신·무선·휴대폰 스택 지연 L은 일정(미측정, 10~20 ms로 가정). `startCapture` 호출 시각을 T, 첫 도착 시각을 A라 하면 A−T는 0~100 ms에 고르게 분포한다. 패킷 첫 샘플은 도착보다 약 90 ms + L 전에 찍혔으므로

- 첫 샘플의 실제 시각 − T ≈ (A−T) − 90 − L → 약 **[−110, 0] ms**. CSV 0 ms는 `startCapture`(시작 비프 호출) 직전에서 약 110 ms 이전 사이에 있고, 그 폭 약 100 ms는 클립마다 무작위다.
- "지금" 신호(T+1000 ms 예약)는 CSV 시각으로 약 1.00~1.11 s + 소리·화면 출력 지연에 해당한다.
- MTU가 작아 1샘플씩 보내면 폭이 약 10 ms로 줄지만 이번 조사에서 확인한 사실은 아니다. MTU 247 협상 성공은 과거 진행기록(`docs/진행기록.md:792`)에 있고, 이번 세션들의 값은 connection_log의 `mtu` 행(`ImuBleClient.java:165`)으로 확인해야 한다.

이 폭은 클립마다 달라 파일럿에서 한 번 재서 보정할 수 없다. 슬롯 번호 저장(A1 변경)이 필요한 이유다.

## 4. 동기화 방식별 평가

### (a) 링 탭(두드림) 표식

| 항목 | 평가 |
|---|---|
| 시각 대응 | CSV의 가속도/자이로 스파이크 시작 샘플과 영상에서 접촉이 처음 보이는 프레임을 연결한다. 영상 소리의 충격음은 교차 확인용이다(오디오-영상 동기 정밀도는 미확인). |
| BLE 지터 영향 | **같은 캡처 안의 상대 시각에는 없음**(슬롯 기반, A1). 탭이 별개 캡처에 있으면 슬롯 번호를 저장해야 연결된다(§1 권장 경로). |
| 불확실성 구성(폭, 추정) | 센서 쪽: 슬롯 10 ms + 비동기 읽기 표본 연령 ≤ 약 9.6 ms + 필터 지연(수 ms, 미확인) ≈ 20 ms. 영상 쪽: 프레임 주기 + 노출/롤링셔터 읽기 시간(이 카메라는 미측정, 가정 약 15 ms). |
| 가속도 포화 | 가속도 범위 ±4 g(`:164`)라 단단한 두드림은 포화할 수 있다. 정점이 아니라 **시작 지점**으로 위치를 잡는다. 자이로는 ±2000 dps. |
| 가이드 4초 클립 안에 넣을 때 | 자동 완료 도구를 오염시킨다(§5). |

영상 FPS별 총 폭(센서 ≈20 ms + 프레임 주기 + ≈15 ms를 선형 합산한 최악 추정, 반폭은 절반):

| FPS | 프레임 주기 | 총 폭(추정) | 반폭 | ≤50 ms 목표 |
|---|---|---|---|---|
| 30 | 33 ms | ≈68 ms | ≈±34 ms | 경계(여유 적음, 비권장) |
| 60 | 17 ms | ≈52 ms | ≈±26 ms | 가능(최소 권장) |
| 120 | 8 ms | ≈43 ms | ≈±22 ms | 가능(권장) |
| 240 | 4 ms | ≈39 ms | ≈±20 ms | 가능(화질·노출 제약) |

"50 ms 이내"를 반폭(±)으로 읽는지 총 폭으로 읽는지가 계획에 명시돼 있지 않다. 총 폭 50 ms로 읽으면 60 fps는 경계이고 120 fps 이상이 필요하다. 파일럿 보고에 어느 정의인지 적는다.

### (b) 보드 LED 표식 (펌웨어 + 앱 변경 필요, 구현하지 않음)

최소 변경안:

1. 펌웨어(F1): 스트리밍 중 `slot % 256 == 0`(2.56 s 주기, 상수는 조정 가능)인 샘플을 읽는 같은 `loop` 반복에서 LED를 30 ms 이상(60 fps에서 2프레임 확보 시 40 ms) 켠다. 기존 heartbeat(`pollLed`, `:341-356`)와 색을 달리하거나 스트리밍 중에는 이것으로 대체한다. 앱→링 명령도 새 특성도 패킷 형식 변경도 필요 없다. 슬롯 번호는 이미 패킷에 있기 때문이다.
2. 앱(A1): 캡처마다 `firstSlot`을 sidecar에 저장. 그러면 모든 클립에서 `(firstSlot + 행번호) % 256 == 0`인 행이 LED 점등 시점이다. 4초 클립마다 1~2회 보이므로 오프셋과 클립 내 드리프트를 클립 자체에서 얻고, 센서에는 탭 충격이 섞이지 않는다.
3. 한계: 링을 착용한 상태에서 LED가 영상에 보이는지 미확인. LED 점등 지연은 루프 1회분(미측정)이고 영상 쪽 불확실성은 프레임 주기 + 노출 정도다. 펌웨어 업로드는 사용자가 직접 해야 한다.

현재 펌웨어의 2초 heartbeat는 슬롯과 연결되지 않으므로 오프셋 표식으로 쓸 수 없다(F5).

### (c) 휴대폰 비프·화면 신호만 사용

| 문제 | 근거 |
|---|---|
| CSV 0 ms가 비프 호출보다 0~110 ms 앞이고 폭 약 100 ms가 무작위 | §3 |
| 비프 호출과 실제 발음 사이 오디오 출력 지연이 비결정적 | A6 |
| "지금" 신호는 CSV 시각이 아니라 메인 핸들러의 `PRE_ROLL_MS` 지연 뒤에 발생 | `MainActivity.java:605-608` |
| 화면 문구는 렌더링 지연이 더해지고, 앱 이벤트 목록은 초 단위 | `:251-256` |

폭만으로도 50 ms 목표를 넘으므로 단독 표식으로 쓸 수 없다. 계획 5절의 판단(앱 비프만으로 0 ms를 정하지 않음)과 일치한다. 참고용 보조 기록으로는 의미가 있다.

## 5. 탭이 자동 완료 도구를 오염시키는 정도 (합성 시뮬레이션)

방법: P1 세션의 `raw_up/down/left/right.1.csv` 사본(스크래치 폴더, 저장소 밖)에 합성 3샘플 펄스(자이로 X +g, Y −0.6g, 가속도 Y +40 m/s², g=150 또는 400 dps)를 넣고 `suggest-gesture-completions.js`를 사본 폴더에 돌렸다. **실제 탭 신호가 아니라 가정한 크기이며 4개 클립 한정 예시다.** 원본은 건드리지 않았다. `raw_down.1`은 탭 없이도 이미 `early_motion`이다.

| 탭 위치 | 관찰 | 도구 코드 근거 |
|---|---|---|
| 0.3 s, 0.7 s (제스처 전) | 4개 클립 모두 e(`completion_ms`)가 변하지 않았다. g=400에서는 4개 모두 `main_motion_start_ms`가 탭 시각(300~700 ms)으로 이동하고 `early_motion`이 붙었다(down은 `second_motion_cluster`도 추가). g=150에서는 up만 시작점이 이동하지 않았다. | 시작점이 활성 구간 에너지 1%이며 단일 펄스도 합산(`:206-208`), `:245-246` |
| 3.7 s (복귀 후 말미) | g=400이면 4개 모두 e가 약 3.7 s로 이동(예: left 2020→3740 ms)하고 `late_completion`. g=150도 left·right에서 이동했고 right는 `no_180ms_settle`도 붙었다. | 에너지 99% 지점과 최종 40행 기준이 탭에 끌림(`:208-216`, `:227-234`, `:247`) |

따라서 가이드 클립 안의 탭은 (i) 이른 위치면 e는 이 예시에서 보존됐지만 도구 플래그를 바꾸고, (ii) 늦은 위치면 e 자체를 바꾼다. 계획 5절의 "표식을 분석 클립 밖에 둔다"를 지키려면 표식은 별도 캡처(연속 기록)에 두어야 한다.

## 6. 3개 파일럿에서 offset·드리프트·오차 범위를 재는 방법

- 각 파일럿: **연속 기록 하나(약 40~60초)와 영상 한 개**. 시작 후 약 3초 정지 → 탭 1 → 동작 1~2회와 자연 복귀(가시성 확인) → 중간 탭 2 → 정지 → 마지막 탭 3 → 3초 더 촬영. 탭은 같은 표면에 같은 방식으로 한다. 2연타(약 0.5 s 간격)로 하면 영상·센서에서 같은 탭끼리 맞추기 쉽다.
- 각 탭 i: 센서 시각 s_i = 스파이크 시작 행의 `timestamp`(ms). 영상 시각 v_i = 접촉 첫 프레임의 **프레임 PTS**(ffprobe 등으로 얻은 실제 타임스탬프이며, 이름뿐인 FPS로 나눈 값은 쓰지 않는다). o_i = v_i − s_i.
- offset = o_i의 평균(또는 선형 적합의 절편). 드리프트 = (o_3 − o_1) / (s_3 − s_1) (ms/s, 1 ms/s = 1000 ppm). 3점 선형 적합의 기울기도 병기한다.
- 4초 클립에서의 드리프트 기여 = |기울기| × 4 s. 해상도: 탭당 오차 σ≈10 ms, 간격 50 s면 기울기 해상도 약 ±0.3 ms/s 이하라 4초 기여는 ±1~2 ms 안으로 한정 가능(추정). 크게 나오면 영상 가변 프레임률이나 시계 문제를 의심한다.
- 오차 범위 = 선형 적합 잔차의 최대값 + §4-a의 시스템 오차 폭(센서 ≈20 ms, 영상 프레임 주기와 읽기 시간). 파일럿 통과 기준(제안): 3개 모두에서 합산 오차가 정한 정의(총 폭 또는 반폭 50 ms)를 넘지 않는다.
- 앱 변경 후 추가 검증: 파일럿 중 가이드 클립 1~2개를 sacrificial로 수행하고(도구에 넣지 않는다), 그 안에서 일부러 탭을 해 **sidecar 슬롯 번호로 예측한 영상 시각**과 **실제로 본 영상 시각**의 차이를 확인한다. 슬롯 기반 대응의 직접 검증이다.
- 한 부팅 안에서만 유효하다. 전원 끄기(3초 이상 누름)나 재부팅 뒤에는 슬롯이 처음부터 다시 세므로 표식을 다시 찍는다. sidecar의 `firstSlot`이 이전보다 작아지면 재부팅이 있었다는 신호다.

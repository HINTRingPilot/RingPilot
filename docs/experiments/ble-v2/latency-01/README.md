# 판정 지연 시간 비교(latency-01)

질문: 판정 한 번에 걸리는 시간이 파이썬(Keras)과 C에서 얼마나 다르고, 보드에서 판정 주기 안에 들어가는가?

모델은 `newtcnrotwarpnoacc` S-P5 seed 20261021 fold 0 E60이다. 시간 측정용이며 최종 모델이 아니다. 같은 입력에서 두 구현의 출력이 같다는 것은 `ml/v2_export_c.py check`로 먼저 확인했다(점수 최대 오차 8.9e-7, 발행 동일).

## 비교 경로

| 경로 | 내용 | 계산량 |
|---|---|---|
| `keras_eager` | `model(x)`를 창 하나씩 호출 | 675,920 MAC |
| `keras_tf_function` | 그래프로 묶은 Keras 호출 | 675,920 MAC |
| `c_predict` | C, 마지막 시점에 필요한 칸만 계산 | 96,368 MAC |
| `python_prepare`, `c_prepare` | 원시 자이로 → 모델 입력 | |

PC 측정은 Keras와 C를 같은 PC, 같은 창, 스레드 1개로 비교한다. 파이썬은 보드에서 돌지 않으므로 보드 결과는 C 하나다. PC 수치로 보드 시간을 추정하지 않는다.

## PC 결과 — 2026-10-31

명령: `RINGPILOT_CC=<컴파일러> ml/.venv/Scripts/python.exe ml/v2_latency.py --tag c-verify-20261031 --out user-pc-20261031`. 다른 학습을 돌리지 않은 상태에서 쟀다. 앞 50회는 버렸다. Keras는 950회, C는 4,950회다. 환경은 `results/user-pc-20261031.json`에 있다(AMD64 PC, Python 3.12, TensorFlow 2.21, zig cc 0.16.0 `-O2`).

| 경로 | 중앙값 | p95 | p99 | 최대 |
|---|---:|---:|---:|---:|
| `keras_eager` | 30.33 ms | 38.24 ms | 41.27 ms | 42.98 ms |
| `keras_tf_function` | 0.725 ms | 1.362 ms | 1.743 ms | 2.389 ms |
| `c_predict` | **0.028 ms** | 0.049 ms | 0.080 ms | 0.713 ms |
| `python_prepare` | 0.080 ms | 0.168 ms | 0.287 ms | 0.672 ms |

- 중앙값 기준 C 추론은 그래프 Keras보다 약 26배, eager보다 약 1,075배 빠르다.
- C가 빠른 것은 계산량 감소(약 7분의 1)와 프레임워크 부담 제거가 합쳐진 결과다. 이 측정으로 둘을 나누지는 않았다.
- PC 결과이므로 Cortex-M4F 시간을 뜻하지 않는다.

## 보드 측정 방법(미실행)

펌웨어: `firmware/gesture_infer`. 시리얼에서 `r`로 통계를 비우고 약 1분 뒤 `l`로 읽는다. `l`은 `gr_push` 한 번의 시간을 DWT 사이클 카운터로 잰 값이다(온라인 영점, 입력 처리, 추론, 발행 규칙 포함). BLE 인터럽트가 끼어든 시간도 들어간다. 이 코어의 `micros()`는 약 977 µs 단위라 판정 시간 측정에 쓰지 않는다. 읽기 간격 값은 `micros()` 기준이라 약 ±1 ms다.

```
arduino-cli compile --fqbn Seeeduino:nrf52:xiaonRF52840Sense --build-path .build/gesture_infer firmware/gesture_infer
arduino-cli upload -p <포트> --fqbn Seeeduino:nrf52:xiaonRF52840Sense --input-dir .build/gesture_infer
```

| 조건 | 설정 | 판정 시간 중앙값/p95/최대 | 재읽기 | 읽기 간격 최대 | 채운 슬롯 | 링 넘침 |
|---|---|---|---|---|---|---|
| A | USB만, BLE 연결 없음, 보드 정지, 30초(2026-10-31 실측) | **14.09 / 14.50 / 14.55 ms** | 190/3,002 (6.3%) | 17.9 ms | 0 | 0 |
| B | 앱 연결, IMU 스트림 구독(지금 수집과 같은 상태) | 미측정 | 미측정 | 미측정 | 미측정 | 미측정 |

코어 1.1.13, `-Ofast`, 64 MHz. 플래시 명령 캐시는 이미 켜져 있었다. 조건 A의 판정 하나는 약 90만 사이클로 MAC당 약 9.4사이클이다. 수집 데이터(수집 펌웨어)의 재읽기는 157,266행 중 1행(0.00%)이다.

### 판정 기준(측정 전에 고정)

1. **판정 시간 p95가 10 ms 미만이고 조건 B의 채운 슬롯이 측정 시간의 판정 수 대비 1% 미만이면 그대로 쓴다.** 50 ms 판정 주기보다 이 기준이 더 엄격하다. 지금 스케치는 샘플링과 추론을 같은 `loop`에서 돌려, 판정이 샘플 주기(10 ms)를 넘기면 다음 읽기가 밀린다.
2. p95가 10 ms 이상 50 ms 미만이면 판정은 제때 끝나지만 읽기 간격이 흔들린다. 읽기를 추론과 분리한 뒤 다시 잰다.
3. p95가 50 ms 이상이면 컴파일 최적화, 스트리밍 추론, int8 순으로 검토한다.

### 조건 A 판정(2026-10-31)

기준 1 미달, 기준 2에 해당한다(p95 14.50 ms). 추정치 6~12 ms보다 느렸다.

- **측정 전 설명을 정정한다.** "10 ms를 넘기면 샘플을 놓치고 직전 값으로 채운다"는 틀렸다. 슬롯은 20 ms를 넘겨야 비고, 채운 슬롯은 0이었다. 실제로는 10~20 ms 칸의 읽기가 약 14 ms에 밀려 일어나 간격이 약 14 ms, 6 ms로 번갈아 나온다.
- 그 결과 센서가 새 값을 내기 전에 읽어 같은 값이 다시 나온다(6.3%, 판정 약 3번에 1번꼴). 그 사이 센서 샘플 하나는 읽지 못했을 수 있다. 수집 데이터에는 거의 없던 패턴(0.00%)이다.
- 이 영향이 인식 성능을 얼마나 바꾸는지는 아직 재지 않았다.
- `NRF_NVMC->ICACHECNF`를 앱에서 바꾸려 하자 보드가 재시작됐다(SoftDevice 보호 영역으로 추정). 해당 시험 명령은 뺐다.

# RingPilot 제스처 인식 시행착오 정리

범위: 2026-10-26~11-03, BLE v2 데이터(자세별 5세션)로 한 모델 실험. 그 전 과정은 [개발 진행 요약 및 실험 회고](개발진행요약_2026-10-25.md)에 있다. 자세한 수치와 조건은 [실험 README](experiments/ble-v2/return-label-01/README.md)와 [진행기록](진행기록.md)에 있다.

검지 반지의 IMU로 위·아래·왼쪽·오른쪽 제스처를 실시간 인식하는 모델을 만들면서, 틀린 가설과 되돌린 결정까지 시도 순서대로 적었다.

## 성능이 바뀐 흐름

정검출은 클립 안에 정답 방향 발행이 있고 다른 방향 발행이 없는 비율이다. seed 5개 평균이고, 각 조건에서 고른 에폭 기준이다. 전부 개발용 교차검증 값이며 실제 사용 성능이 아니다.

| 단계 | 바꾼 것 | C | S-P5 | 채택 |
|---|---|---:|---:|---|
| 기준선(10-25) | 2층 CNN, 완전히 멈춘 시점 e를 정답으로 | 17.8%* | 34.4%* | |
| 채점 변경 | 채점 구간을 복귀 피크~r+500으로 | 79.4% | 63.3% | ○ |
| 라벨 변경 | 정답 시점을 r(복귀 도중)로 | 74.0% | 68.5% | ○ |
| 입력 추가 | 회전각 3채널 | 84.3% | 70.2% | ○ |
| 모델 변경 | TCN | 91.0% | 80.2% | ○ |
| 스케일 수정 | 회전각 정규화 | 95.9% | 91.1% | ○ |
| 실시간화 | 회전각 영점을 동작 전 구간에서 | 95.6% | 90.0% | ○ |
| 증강 1 | 회전 사본 | 98.4% | 94.0% | ○ |
| 증강 2 | 속도 변형 | 98.4% | 95.3% | ○(뒤늦게) |
| 채점 변경 | 채점 구간을 끝점~r+300으로 | 98.6% | 96.9% | ○ |
| 입력 제거 | 가속도 3채널 제외 | 98.3% | 96.7% | ○ |

\* 다른 방향 발행을 허용한 옛 지표(`success_rate`)이고 채점 구간도 달라, 아래 행과 직접 비교할 수 없다. 채점 변경 행도 앞뒤 비교가 아니라 기준이 바뀐 것이다.

마지막 행의 진짜 효과는 이 표에 보이지 않는다. S-P5는 가장 유리한 분할이었고, 다섯 S 분할 평균으로 보면 91.98%에서 97.06%로 올랐다(6번 항목).

## 시도별 기록

### 1. 낮은 점수의 큰 부분은 모델이 아니라 채점이었다

- **증상:** 기준선 정검출이 10~30%대라 모델이 형편없어 보였다.
- **시도:** 모델을 바꾸기 전에 정답 시점과 채점 구간을 봤다. 정답 시점 e는 복귀 뒤 작은 떨림까지 기다려 늦게 잡혔고, e 앞뒤 창은 거의 같았다(50 ms 변화 중앙값 6.8 dps, 복귀 피크의 2%).
- **결과:** 같은 모델을 채점 구간만 바꿔 매기자 9.6~35.9%에서 50.7~93.9%가 됐다. 정답을 r(복귀 피크 뒤 주축 자이로가 절반으로 내려온 시점)로 옮기자 발행 지연이 약 180 ms 줄고 배경 오발행이 절반 안팎으로 줄었다.
- **배운 점:** 점수가 낮으면 모델을 고치기 전에 자로 쓰는 정답과 지표부터 의심한다.

### 2. 반대 방향 조기 발행: 틀린 가설 세 번 끝에 측정으로 찾았다

r로 옮기자 새 문제가 생겼다. "위" 동작이 끝점에 다다르는 순간을 "아래" 동작의 복귀로 착각해 반대 방향을 발행했다.

| 가설 | 시도 | 결과(반대 방향 조기 발행) | 판정 |
|---|---|---|---|
| 헷갈리는 NONE 예시가 부족하다 | 끝점 근처 창을 NONE으로 추가(newhard) | 355 → 596건, 악화 | 실패 |
| 추가한 창의 범위가 틀렸다 | 끝점 이하 창으로 좁힘(newpre) | 355 → 342건 | 실패 |
| 앞선 움직임 정보를 못 쓴다 | 회전각 채널 추가(newangle) | 355 → 221건 | 일부 효과 |
| 수용 영역이 좁다 | TCN으로 변경(newtcn) | 221 → 248건. 정검출은 크게 올랐지만 이 오류는 그대로 | 다른 효과 |
| NONE 예시 부족(재시도) | TCN + NONE 추가(newtcnhard) | 줄지 않음 | 실패 |

- **전환점:** 추측을 멈추고 가리기 측정을 했다. 입력의 구간과 채널을 하나씩 0으로 바꿔 판정이 어떻게 변하는지 봤더니, 모델은 최근 0.1~0.2초 자이로 피크만 보고 회전각은 거의 쓰지 않았다.
- **원인:** 회전각 채널은 값이 1 안팎이라 수 단위로 정규화된 자이로보다 영향력이 약했다. 정보를 줬는데도 크기가 작아 무시된 것이다.
- **해결:** 회전각도 학습 창의 평균·표준편차로 정규화했다. 두 분할 합계 82 → 21건(−74%), S-P5 정검출 80.2 → 91.1%. 가리기 측정을 다시 해 모델이 실제로 회전각을 쓰는 것을 확인했다.
- **배운 점:** 구조를 키우기 전에 모델이 입력을 실제로 쓰는지 잰다. 이번 최대 개선은 코드 몇 줄의 스케일 수정이었다.

### 3. 속도 증강: 결론을 바꾼 것은 데이터가 아니라 기준이었다

- **시도:** 회전 사본을 추가해 S-P5 정검출이 90.1 → 94.0%로 올라 채택했다. 이어서 속도 변형을 시험했다.
- **결과:** S-P5 94.0 → 95.3%(seed 5/5 개선)인데 배경 오발행이 C 0.173 → 0.247로 늘어, 결과 전에 정한 기준에 따라 미채택했다.
- **뒤집힘:** 이후 프로젝트 우선순위를 정검출 우선으로 정리하고, 약한 동작도 조작으로 받기로 해 채택했다. 약한 동작 정검출은 S-P5에서 60.0 → 78.5%였다.
- **배운 점:** 사전 기준은 결과를 보고 고르는 일을 막아 주지만, 기준이 제품 우선순위를 반영하지 않으면 맞는 절차로 틀린 답을 낸다. 기준을 바꿀 때는 이유를 기록한다.

### 4. 약한 동작: 하루에 결정이 세 번 바뀌었다

P1 세션의 무발행을 진단했더니 점수가 판정 한 번만 짧게 솟았고, 해당 동작은 약하고 빨랐다.

| 결정 | 내용 | 결과 |
|---|---|---|
| 1 | 약한 동작 14개(같은 방향 중앙값의 0.6배 미만)를 학습·평가에서 제외 | 수치가 오른 듯 보임 |
| 2 | 학습에는 넣고 평가에서만 제외 | 같은 클립·같은 PC로 비교하니 학습에서 뺀 쪽의 무발행이 25 → 66건(S-P5 E20) |
| 3 | 평가에도 포함하고 검출률은 따로 보고 | 약하게 움직여도 조작되면 피로가 준다는 판단 |

- **함정:** 1번 뒤 오른 수치의 대부분은 평가에서 어려운 클립이 빠진 효과였다. 이전 모델을 남은 클립으로만 다시 채점해도 같은 수치가 나왔다.
- **배운 점:** 데이터를 빼고 성능을 비교할 때는 같은 클립으로 다시 채점한다. PC가 다르면 같은 seed도 최대 5.5%p 차이가 나므로 같은 PC에서 기준선을 다시 만든다.

### 5. 규칙과 라벨로 무발행을 줄이려 한 시도들

- **발행 문턱 0.8 → 0.7:** 무발행 25 → 15건, 대신 다른 방향과 조기 발행이 합쳐 17 → 26건. 정검출은 그대로였다. 오류가 다른 칸으로 옮겨 갔을 뿐이다.
- **부드러운 라벨:** 경계 창에 0과 1 사이 목표를 줘 점수 봉우리를 넓히려 했다. 예상과 반대로 점수 최고값이 낮아져 문턱 0.8에서 95.78 → 93.00%가 됐다. 코드는 되돌리고 기록만 남겼다.
- **연속 3회 규칙:** 다른 방향 발행 49 → 12건으로 크게 줄었지만 정검출 −2.2%p, 지연 +50 ms였다. 잘못된 명령과 놓친 명령의 교환 관계가 드러났다.
- **배운 점:** 재학습 없이 저장된 점수로 먼저 시험하면 싸게 걸러진다. 후처리는 오류를 없애기보다 종류를 바꾸는 경우가 많다.

### 6. 가장 큰 발견: 시간을 아끼려 줄인 분할이 약점을 가리고 있었다

- **경과:** 10-27에 시간을 아끼려고 실험을 C·S-P5 두 분할로 줄였다. 10-29에 나머지를 돌렸더니 S-P5 96.88%와 달리 S-P3 88.94%, S-P4 88.21%였고 평균은 91.98%였다. S-P5는 다섯 분할 중 가장 유리한 경우였다.
- **단서:** 무발행이 특정 검증 세션에 몰렸다. 세션별 손목 방향(중력 방향)을 재 보니 P1–P2가 20°, P3–P4가 59°로 짝을 이뤘다. 짝이 둘 다 학습에서 빠지면 무발행이 급증했다.
- **원인:** 같은 동작의 회전은 반지 기준으로 세션 간에 거의 같았고(코사인 유사도 0.78~0.99), 가속도 변화는 크게 달랐다(−0.64~0.96). 가속도에 섞인 중력이 처음 보는 자세에서 방해가 된 것으로 해석했다.
- **해결:** 가속도 3채널을 뺐다. S-P3 88.94 → 97.45%, S-P4 88.21 → 97.26%, S 평균 91.98 → 97.06%(seed 개선 S-P2·S-P3·S-P4 5/5, S-P1 4/5와 동률 1), 무발행 합 434 → 118건.
- **대가:** 다른 방향 발행이 여섯 분할 합 40 → 62건으로 늘었다. 시작 자세의 중력만 뺀 가속도를 다시 넣어 봤지만(accsub) S 평균 95.95%로 떨어져 미채택했다.
- **배운 점:** 평가 분할을 줄이는 결정은 시간만이 아니라 볼 수 있는 약점도 줄인다. 입력을 더 넣는 것이 늘 좋지는 않다. 일반화에 해로운 입력은 빼는 편이 낫다.

### 7. 지표가 제품 의도와 어긋났던 경우

- **증상:** 같은 방향 조기 발행이 오류의 26%(13건)를 차지했다.
- **확인:** 13건 모두 손이 이미 돌아오는 중이었고, 복귀 피크보다 10~60 ms 이른 판정이었다. 옳은 방향이면 빠른 발행은 오히려 좋다.
- **조치:** 채점 시작을 복귀 피크에서 끝점으로 당겼다. 끝은 r+200을 시험했다가 늦은 발행 6건을 보고 r+300으로 정했다(실기기 체감 확인 전 잠정값).
- **배운 점:** 오류 건수만 세지 말고 사례를 열어 본다. 다만 지표를 바꿔서 오른 수치는 모델 개선이 아니므로 구분해서 적는다.

### 8. 데이터와 실행에서 겪은 일

- **USB 데이터 폐기(10-21):** 케이블의 무게와 당김이 동작에 섞여 무선 사용을 대표하지 못한다고 판단했다.
- **BLE v1 세션 폐기(10-23):** 펌웨어(±2000 dps)와 앱 환산(±1000 dps)이 어긋나 자이로가 절반으로 기록됐을 가능성이 있었다. 펌웨어를 올릴 때 앱 버전과의 짝을 확인하지 않은 것이 원인이다.
- **라벨 감사:** 다른 방향을 한 클립은 없었고, 자동 라벨 오류 1개와 신호 전 손 회전으로 영점이 틀린 1개를 찾아 뺐다.
- **파생 파일 삭제:** 세션을 지울 때 주석과 결과까지 재현 불가가 된다는 점을 먼저 알리지 못했다.
- **긴 학습 중단:** PC 대기 모드로 학습이 약 1시간 40분 멈췄다. 결과에는 영향이 없었고, 이후 실행 중 대기를 막는 래퍼를 썼다.
- **메모리 부족:** 학습을 많이 병렬로 돌리거나 다른 TensorFlow 작업과 겹치면 실패했다. 병렬 수를 줄이고 무거운 작업을 같이 돌리지 않기로 했다.

### 9. 좌우 제스처를 상하·좌우 전환으로 통합

좌우 제스처를 구분 없이 모드 전환으로 쓰고, 위·아래 제스처만으로 네 방향을 조작하게 바꿨다. 좌우 모드에서는 위가 왼쪽, 아래가 오른쪽 스와이프가 된다. 움직인 방향과 화면 방향이 항상 같다는 직관성은 일부 잃지만, 좌우로 움직일 공간이 좁아 불편하다는 점을 고려해 사용자의 편의성을 우선했다. 좌우 혼동 오류도 사라진다(S 평균 정검출 97.06 → 97.52%, 저장 결과 재계산). 전환 오발행은 다시 전환하면 되돌릴 수 있어 감수했다. 유튜브와 네이버 시리즈에서 동작을 사용자가 확인했다.

뒤에 현재 앱 규칙으로 저장 모델을 다시 채점했다(2026-11-03). 걱정했던 이중 전환(한 동작에 전환 두 번)은 입력 지우기 뒤 0건이었다. 네 방향 평균이 가리던 약점도 드러났다. 지금 주로 쓰는 위·아래는 96.1%·96.9%이고 그중 아래가 93.4%·95.7%로 가장 낮다. 입력 방식을 바꾸면 평가 기준도 함께 바꿔야 한다는 교훈이다.

### 10. 연속 동작 무발행: 비싼 학습보다 작은 입력 처리로 풀렸다

바로 이어서 동작하면 인식이 안 됐다. 33초 연속 기록을 재생해 보니 잠금은 먼저 풀려 있었고 모델 점수가 낮았다. 입력을 바꿔 재생하자 빠른 구간은 앞 동작을 정지 값으로 지웠을 때 점수가 약 1.00으로 회복됐고 회전각 기준·세기·속도를 바꿔서는 회복되지 않아, 판정 창에 남은 앞 동작의 영향으로 좁혔다(자이로와 회전각을 함께 지운 조작이라 채널 하나로 확정하지는 않았다).

처음 시도한 앞 동작 합성 학습은 빠른 반복을 늘렸지만 단일 clean이 떨어지고 other 오발행이 3~4배가 돼 보류했다. 진단에 쓴 "지우기"를 발행 뒤 실제 처리로 옮기자, 재학습 없이 같은 33초 기록의 빠른 위 정답이 36 → 100/100이 됐다(같은 동작 5개를 모델 20개로 재생한 합이라 독립된 100회가 아니다). 편한 간격 오답도 18·17 → 0이 됐고 단일 clean은 떨어지지 않았다.

대가도 있다. 일상 동작 발행이 29 → 42, 19 → 36(160회 기준)으로 늘어 사전 기준에는 미달이었다. 이를 알고 보드에 올렸고, 쓰지 않을 때 일시정지하는 사용법으로 부담을 줄였다. 사용자 체감은 "아주 잘 됨"이지만 측정은 아니다.

### 11. 5방향 스위치 포인터: 부품의 조작감은 실물로만 알 수 있었다

엄지로 5방향 스위치를 밀어 커서를 움직이는 포인터를 만들었다. 처음에는 BLE 마우스(HID)로 했다가, 커서를 평소 숨기고 쓸 때만 보이게 하려고 앱이 커서를 그리는 방식으로 바꿨다(HID는 폰이 커서를 관리해 숨는 시간을 정할 수 없다). 보드에서 방향 4개와 클릭 입력, 방향 매핑까지 확인했다(2026-11-16).

그런데 실제로 눌러 보니 부품이 실사용에 맞지 않았다. 스위치(SKRHACE010)가 빡빡해 밀 때 저항이 강하고, 밀면 반지에 붙인 접착부가 조금 밀린다. 단단히 고정해도 스위치 머리가 각져 있어 손가락이 아프다. 커서처럼 자주, 오래 미는 입력에는 불편할 것으로 판단했다. 기능 코드는 남겨 두었다.

이는 부품 자체의 한계로 남긴다. 사양표의 작동력 숫자만으로는 손가락에 끼운 상태의 느낌을 알 수 없고, 이런 작은 부품은 사용 후기도 찾기 어려워 사서 써 보기 전에는 확인할 방법이 마땅치 않았다.

## 되풀이된 교훈

1. **원인을 측정한 뒤 고친다.** 가리기 측정과 손목 방향 각도 측정이 가장 큰 두 개선을 이끌었다. 추측으로 넣은 NONE 추가는 세 번 다 실패했다.
2. **자를 먼저 검증한다.** 정답 시점과 채점 구간이 결과를 크게 좌우했다.
3. **비교 조건을 맞춘다.** 같은 PC, 같은 클립으로 한 번에 한 요인만 바꾼다.
4. **유리한 분할 하나로 판단하지 않는다.** 평균이 좋아도 특정 조건에서 무너질 수 있다.
5. **실패와 뒤집힌 결정도 남긴다.** 코드는 되돌려도 기록을 남겨 같은 시도를 반복하지 않았다.

## 아직 모르는 것

- 지금 수치는 개발용 교차검증이다. 334개 클립이 모두 개발에 쓰여 독립 평가 자료가 없다.
- 실제 연속 사용 성능은 수치로 재지 않았다. 클립 평가는 상태를 초기화하고, 연속 자료는 33초 기록, 실사용 기록 2개(약 130초·66초, 사람이 확인한 정답 없음), 사용자 체감뿐이다.
- 명령이 아닌 움직임(other)에서 오발행이 클립당 0.202건 나온다. 일부러 헷갈리게 모은 자료지만 정검출보다 큰 위험일 수 있다.
- 보드 판정 시간은 쟀지만(p95 약 22 ms) 동작부터 화면 반응까지의 지연은 체감만 있고 수치가 없다. 전력도 재지 않았다.
- 시작 간격 약 0.55초의 빠른 동작, 전환 직후 조작, 다른 앱을 쓰며 오래 사용할 때의 연결 유지는 확인하지 못했다. 실제 시험 간격의 번갈아는 동작 후보 기준 34/40, 17/20이었다(인식률 아님, [field-02](experiments/ble-v2/field-02/README.md)).
- 하이퍼파라미터 튜닝은 아직 하지 않았다.

# RingPilot 개발 진행 기록

포트폴리오 작성에 사용할 사실 기반 개발 일지. 날짜는 한국 시간 기준.
각 작업마다 목적 → 수행 내용 → 선택 이유 → 검증 결과/증거 → 문제와 해결 → 다음 작업을 기록한다.
계획, 실제 수행, 사용자 확인을 구분하고 미검증 성능을 성과로 쓰지 않는다.
버전, 오류 원문, 관련 코드 경로, 측정 조건과 결과도 확보되는 대로 남긴다.

- BLE PoC 컴파일·업로드·USB 시리얼 응답·Galaxy S10 페어링 및 좌우 포인터 이동 검증 완료.

- Custom GATT 알림 수신과 HID 포인터 이동의 동시 동작 및 USB 전원 재연결 후 두 기능 복구는 2026-09-20 사용자 실화면 확인 완료.
- 휴대폰 Bluetooth OFF/ON 후 포인터·숫자 갱신 복구 사용자 확인 완료. 앱 강제 종료·재실행 후에는 수동 CONNECT로 숫자 수신 복구, 별도 알림 버튼 조작 불필요 확인. 복구 시간은 측정하지 않음.

- 다음: [재수집 계획](TrainingPlan.md#재수집-계획--2026-10-25)(2026-10-25 작성)대로 새 앱으로 재수집하고 `session_info.txt`의 `gyro_range_dps=2000` 확인, `ml/` 코드의 세션 이름·분할을 새 데이터에 맞게 갱신, 스위치 방향 매핑.

## 2026-09-14 — 설치 전 개발환경 선택 검토

- 사용자 질문: Arduino IDE가 일반적인 선택인지, STM32CubeIDE에 대응하는 Seeed 전용 환경이 있는지 확인 요청.
- 공식 문서 확인: Seeed의 XIAO 시작 안내는 Arduino IDE를 사용하며 PlatformIO 안내도 제공한다. Nordic은 nRF Connect SDK용 공식 IDE 환경으로 VS Code + nRF Connect 확장을 제공한다.
- 구분: Seeed는 해당 개발 보드 제작사, Nordic은 탑재 nRF52840 칩 제조사. 칩 제조사 SDK 관점의 대안은 nRF Connect SDK(Zephyr 기반).
- Arduino IDE와 Arduino 프레임워크는 별개 층이다. PlatformIO에서 Arduino 코드를 쓰는 것과 Zephyr로 프레임워크를 바꾸는 것은 변경 범위가 다르다.
- 권고: 빠른 통신 PoC에는 기존 Arduino/Bluefruit 경로가 적절하다. RTOS·BLE 내부 제어 학습을 주요 목표로 삼는다면 Nordic SDK 경로를 시작부터 고려할 수 있다.
- Zephyr 공식 문서에 XIAO BLE Sense 보드 및 UF2 업로드 경로가 존재함을 확인. 특정 nRF Connect SDK 버전에서의 보드 지원·부트로더/메모리 설정은 아직 검증하지 않음. 중단점 디버깅에는 SWD 연결 및 외부 디버거 구성이 필요하다.
- 상태: 비교 설명만 수행. 설치 실행이나 개발환경 변경 확정은 하지 않음.

## 2026-09-14 — 업로드 포트 소실 오류 진단

- 사용자 업로드 로그: 컴파일 성공 후 DFU 업로드에서 `Serial port could not be opened on COM3`, `FileNotFoundError(2)` 발생.
- precompiled nRFCrypto 안내는 실패 원인이 아니며, 실제 오류는 업로드 대상 COM3를 열 수 없다는 내용.
- 에이전트 재조회: SerialPort API에서 포트 없음. 권한 확장한 Arduino CLI `board list`도 `No boards found.`. 연결 가능한 COM 포트나 이동식 볼륨을 확인하지 못함.
- 따라서 현재 포트 번호만 바꿔 재시도할 수 없는 상태. 포트 소실의 근본 원인(USB 연결/실행 펌웨어/부트로더 전환 등)은 미확정.
- 공식 Seeed 문서의 RST 두 번 누르기 부트로더 진입 절차 확인: https://wiki.seeedstudio.com/XIAO-nRF52840-Zephyr-RTOS/
- 다음 작업: 사용자에게 USB 연결 상태 유지 및 RST 빠르게 두 번 누르기 요청. 인식 복구 후 에이전트가 포트 재조회 및 CLI 업로드 진행 예정.
- 현재까지 이번 오류 뒤 업로드 재시도나 부트로더 변경은 수행하지 않음.
- 사용자 USB 분리/재연결 후 재검사: CLI `No boards found.`, SerialPort 목록 없음. XIAO VID_2886/이름에 해당하는 PnP 장치 및 이동식 볼륨도 조회 결과 없음.

## 2026-09-28 — Edge Impulse 제스처 수집환경 준비

### 목적과 선택

- XIAO nRF52840 Sense의 IMU 제스처가 상하좌우 명령으로 분리 가능한지 Edge Impulse에서 빠르게 검증할 수 있는 수집환경을 준비했다.
- 이미 실물 검증된 Bluefruit BLE 펌웨어가 Seeed non-mbed 코어에 의존하므로 코어를 mbed-enabled로 교체하지 않았다. 데이터 수집은 별도 스케치로 분리하고, 추후 생성 모델을 현재 코어에서 먼저 컴파일 검증한 뒤 BLE 코드에 통합하기로 했다.
- 방향 동작 외에 `idle`과 `other` 라벨을 포함하도록 안내했다. 실제 사용 중 비명령 동작으로 인한 오작동을 측정하고 억제하기 위한 선택이다.

### 설치 및 변경

- 기존 설치 확인: Node.js `24.18.0`, npm `11.16.0`, Arduino IDE 동봉 CLI `1.5.1`, Seeed nRF52 Boards(non-mbed) `1.1.13`.
- Edge Impulse CLI `1.40.0`을 npm 전역 도구로 설치했다. 실행 파일 위치는 `%APPDATA%\npm`이며 사용자 PATH에 해당 경로가 포함된 것을 확인했다.
- Seeed Arduino LSM6DS3 `2.0.7`을 Arduino 사용자 라이브러리에 설치했다.
- `firmware/imu_capture/imu_capture.ino` 추가: LSM6DS3TR-C를 I2C 주소 `0x6A`로 초기화하고 가속도 ±4 g, 자이로 ±1000 deg/s, 센서 ODR 104 Hz로 설정했다. USB 출력은 115200 baud, 100 Hz 고정이며 `accX,accY,accZ,gyrX,gyrY,gyrZ` 순서로 출력한다. 가속도는 g에서 m/s²로 변환한다.
- `tools/start-edge-impulse.cmd` 추가: PowerShell 실행 정책을 변경하지 않고 Data Forwarder를 100 Hz로 시작한다.
- `docs/EdgeImpulse.md`에 업로드, 축 이름, 데이터 라벨, 초기 수집량, 모델 권장값, 복구 절차를 작성하고 README 및 설치 안내에서 연결했다.

### 검증 결과

- IMU 수집 스케치를 `Seeeduino:nrf52:xiaonRF52840Sense` 대상으로 컴파일 성공했다. 프로그램 저장 공간 `50,768 / 811,008 bytes (6%)`, 전역 변수 `7,692 / 237,568 bytes (3%)`.
- `tools\start-edge-impulse.cmd --version` 실행 결과 `1.40.0`을 확인했다.
- Edge Impulse CLI가 사용하는 Node serialport 모듈 로드 및 포트 열거에 성공했고 현재 연결된 `COM3, COM4`를 반환했다. 이 두 포트는 기존 확인상 Bluetooth 직렬 포트이며 XIAO 포트는 현재 나타나지 않았다.

## 2026-09-28 — COM6 IMU 펌웨어 업로드 및 Edge Impulse 연결 복구

### 문제와 원인

- 사용자 보고: Edge Impulse CLI 로그인 후 COM6을 선택했지만 연결이 진행되지 않음.
- COM6을 DTR/RTS 활성 상태로 열고 `?`를 전송하자 `SmartRing-PoC` 도움말과 BLE 연결 상태가 응답했다. COM6에는 IMU 수집 펌웨어가 아니라 기존 BLE PoC 펌웨어가 남아 있던 것이 원인이었다.
- DTR/RTS 없이 처음 조회했을 때는 수신 바이트가 0이었다. XIAO의 USB CDC 상태를 정확히 확인하기 위해 이후 조회에서는 DTR/RTS를 활성화했다.

### 수행 및 검증

- 기존에 컴파일한 `firmware/imu_capture/imu_capture.ino`를 COM6에 업로드했다. DFU 중 COM7로 전환된 뒤 `Device programmed.`와 실행 포트 COM6 복귀를 확인했다.

- 정지 상태 평균 가속도 벡터 크기 `9.8049 m/s²`, 평균 자이로 XYZ `0.004, -2.565, -0.117 deg/s`를 확인했다. 짧은 정상 동작 확인값이며 오프셋 보정 결과가 아니다.
- Data Forwarder `1.40.0`을 다시 실행해 COM6을 선택했다. CLI가 장치 ID `D6:20:CB:6F:93:75:50:02`, 100 Hz, 6개 축을 감지했다.
- 축 이름을 `accX,accY,accZ,gyrX,gyrY,gyrZ`로 설정했고, 사용자가 앞서 선택한 Edge Impulse 프로젝트 `Linecoru-project-1`에 장치 연결 성공 메시지와 Data acquisition 주소가 출력됐다.

## 2026-09-28 — TinyML-only windowing 확정안 비판적 검토

- 목적: 사용자 제공 확정안의 구현 가능성과 window 라벨/복귀/중복 검출 위험을 분석한다.

- 기존 움직임 게이트 및 복귀 제외 수집 제안은 폐기하고 EdgeImpulse 안내에 이전 제안임을 표시했다. 원안 파일은 보존했다.
- `docs/Windowing검토.md` 작성: 왕복이 창보다 길 때의 맥락 소실, W-D와 stride/debounce의 관계, 완전 포함 기준의 라벨 계약 후보, 부분 창/NONE 충돌, 반복 명령과 NONE 재무장 교환관계를 분석했다.
- 검증 계획: 자연 복귀를 보존한 원시 연속 기록 → 세션별 분리 → causal window 생성 → TinyML 학습 → 전체 연속 replay에서 이벤트 일대일 평가 → MCU 시간·샘플 누락·메모리 확인.
- 보드 100 Hz에서 400 ms는 40×6 값(원시 float32 960 bytes), 50 ms는 5샘플임을 계산했다. 25 ms stride는 2.5샘플이므로 별도 시간 스케줄 정책이 필요하다.
- 공식 SDK에서 run_classifier blocking 동작을 확인했다. 추론이 50 ms 이내라는 것만으로 10 ms 샘플링 유지가 보장되지 않음을 구현 주의점으로 기록했다.
- 결과/한계: 설계 검토 및 문서 갱신만 완료. 실사용 제스처 원시 데이터·모델 성능·FP/hour·지연을 측정하지 않았다. 원격 프로젝트와 데이터 라벨, 보드 펌웨어는 변경하지 않았다. 다음은 원시 연속 수집/주석 및 replay 평가 도구를 우선 준비하는 것.

## 2026-09-28 — 장기 맥락 기반 현재 이벤트 검출 구조 제안

- 사용자 요청: 기존 문서를 참고하되 제약을 절대시하지 않고 앞선 위험을 고려한 최적 구조를 새로 구상한다.

- 이유: 관찰 길이(초기 1200 ms)와 완료 후 양성 목표 폭(초기 150 ms)을 분리해 복귀 맥락을 유지하고, 오래된 동작이 입력에 남아도 재발행하지 않도록 학습 목표를 바꾼다. NONE은 정지가 아니라 현재 새 이벤트 없음으로 정의한다.

## 2026-09-28 — 800/1200/1600 ms causal window 1차 비교

### 목적과 방법

- 완료 시점 주석을 실제 causal window로 변환해 입력 길이 후보를 줄였다.

- AUTO 30개를 방향별로 층화하고 동일 3초 원본의 window가 train/test에 섞이지 않도록 그룹화한 5-fold 교차검증을 사용했다. REVIEW 10개는 학습에서 제외하고 별도 stress set으로 평가했다.
- 100 Hz 6축 입력, 50 ms stride, 완료 후 150 ms 방향 목표, 그 밖의 `NONE`을 사용했다. 진단 모델은 10개 시간 bin의 6축 평균·표준편차와 양 끝 차이로 만든 126개 특징을 입력하는 635-parameter 선형 softmax다. 같은 방향 2회 연속 검출, NONE 2회 연속 재무장 후처리를 적용했다.

### 결과와 결정

- 800 ms: 주동작 시작 맥락 포함 6/30(20.0%), 이벤트 검출 6/30(20.0%), 목표 밖 이벤트 51개(3초 clip당 1.700), NONE window 오검출 21.83%, 방향 macro F1 0.2163.
- 1200 ms: 맥락 포함 19/30(63.3%), 이벤트 검출 12/30(40.0%), 목표 밖 이벤트 40개(clip당 1.333), NONE 오검출 22.25%, macro F1 0.2532.
- 1600 ms: 맥락 포함 28/30(93.3%), 이벤트 검출 8/30(26.7%), 목표 밖 이벤트 38개(clip당 1.267), NONE 오검출 19.97%, macro F1 0.2718.
- 원시 float32 입력 버퍼는 각각 1920/2880/3840 bytes다. 1600 ms는 1200 ms보다 960 bytes 크다. 모델 tensor arena와 실제 연산량은 포함하지 않은 값이다.
- 800 ms는 맥락 부족이 명확하고 다른 지표도 개선되지 않아 주 후보에서 제외했다. 다음 causal CNN/TCN은 1600 ms를 기본 후보로, 이벤트 recall이 상대적으로 높았던 1200 ms를 비교군으로 유지한다.

### 2026-10-19 추가 조사 — 충전 전류 확인 시도

- 에이전트가 웹에서 XIAO nRF52840 충전 전류 디폴트와 401020 55mAh 셀의 허용 충전 전류를 조사했다. 결론을 내리지 못했고, 불확실성만 확인했다.
- XIAO nRF52840: 충전 전류는 P0.13(HICHG) 핀으로 50mA/100mA 중 선택되는 구조이나, Seeed 포럼 내에서도 핀 극성과 디폴트값에 대한 설명이 서로 엇갈린다. 이 프로젝트가 쓰는 non-mbed 부트로더에서는 P0.13 제어 자체가 인식되지 않고 다른 핀을 써야 한다는 보고도 있어, 현재 보드가 50mA인지 100mA인지 코드나 문서만으로는 확정할 수 없다.
- 401020 55mAh 셀: 공식 제조사 데이터시트를 찾지 못했고 유통업체 판매 페이지만 확인했다. 대부분 1C(55mA)를 최대 충전전류로 표기하며, 더 보수적으로 0.5C(27.5mA)를 권장하는 곳도 있다.
- 평가: 셀이 50mA 충전이면 1C 범위 안, 100mA면 약 1.8C로 통상 권장 범위를 넘는다. 어느 쪽인지 확정하려면 충전 중 실제 전류를 멀티미터로 직렬 측정해야 한다. 아직 측정하지 않았다.
- 출처: [XIAO Sense nRF52840 충전 전류 가이드(Seeed 포럼)](https://forum.seeedstudio.com/t/xiao-sense-nrf52840-a-guide-on-how-to-set-battery-charging-current-0ma-vs-50ma-vs-100ma-non-mbed/276351), [충전이 3.7V에서 멈추는 문제(Seeed 포럼)](https://forum.seeedstudio.com/t/xiao-nrf52840-sense-charging-consistently-stalls-at-3-7v-never-reaches-4-2v/295688)
- 다음: USB+배터리 재연결 전에 멀티미터로 충전 전류 실측. 배터리 셀 구매처에 허용 충전 전류 직접 문의하는 것도 고려.
- **충전 전류 50mA일 가능성이 높다는 추가 단서**: 충전 전류는 nRF52840의 P0.13(HICHG) 핀으로 결정되며, 이 프로젝트가 쓰는 non-mbed 코어(`Seeeduino:nrf52:xiaonRF52840Sense`)에서는 코드상 핀 번호 `22`로 접근한다. Seeed 포럼 실측 기준 핀을 아무것도 건드리지 않거나 `INPUT`으로 두면 50mA(기본값), LOW면 100mA, HIGH면 0mA(충전 꺼짐)이다. `firmware/battery_test/battery_test.ino`, `firmware/switch_test/switch_test.ino`, `firmware/power_off_test/power_off_test.ino`를 다시 확인한 결과 세 코드 모두 pin 22를 전혀 건드리지 않으므로, 지금까지의 배터리 연결 테스트는 기본값인 **50mA로 진행됐을 가능성이 높다**. 50mA라면 401020 55mAh 셀의 1C(55mA) 권장 범위 안에 들어온다.
- 다만 이는 "코드가 안 건드렸으니 기본값일 것"이라는 추론이며 직접 실측하거나 확인한 사실은 아니다. 확인할 기회가 생기면 ① `pinMode(22, INPUT);`을 코드에 명시해 상태를 고정하고 ② 멀티미터 또는 USB 인라인 전류계로 직접 재서 확정한다.
- 출처: [XIAO Sense nRF52840 충전 전류 설정 가이드(Seeed 포럼, pin 22=P0.13/HICHG 매핑과 실측값 포함)](https://forum.seeedstudio.com/t/xiao-sense-nrf52840-a-guide-on-how-to-set-battery-charging-current-0ma-vs-50ma-vs-100ma-non-mbed/276351)

## 2026-10-19 — IMU 6축 BLE 스트리밍 펌웨어 작성

- 목적: 지금까지 IMU 수집(`imu_capture`, USB 시리얼 전용)과 BLE(`ble_poc`, IMU 없음)가 별도 펌웨어라 동시에 돌지 않았다. USB 없이 배터리만으로 무선 IMU 수집과 배터리 단독 BLE 동작을 함께 시험하기 위해 `firmware/imu_ble_stream/imu_ble_stream.ino`를 추가했다.
- 설계:
  - IMU 설정은 `imu_capture`와 동일(100 Hz, ±4 g, ±1000 dps).
  - 패킷: `[첫 샘플 슬롯 uint32][샘플 수 uint8]` + 샘플당 6축 int16(가속도 mg, 자이로 0.1 dps).
  - 협상된 MTU에 맞춰 한 알림에 최대 10개 샘플을 묶는다(대기 지연 약 100 ms 이하). 큰 MTU를 위해 `configPrphBandwidth(BANDWIDTH_MAX)`와 연결 후 MTU/데이터 길이/PHY 갱신을 요청한다.
- 샘플 누락 처리: 코어의 알림 전송이 송신 버퍼가 차면 대기할 수 있어(`getHvnPacket`, 세마포어 대기) 샘플링이 밀릴 수 있다. 샘플마다 부팅 후 10 ms 슬롯 번호를 붙여 빠진 샘플이 숨겨지지 않고 수신 쪽에서 간격으로 드러나게 했다. 링 버퍼(256개) 초과 시 가장 오래된 샘플을 버리고 개수를 센다.
- 센터 스위치(D1) 1초 누름: BLE 연결을 먼저 끊고 IMU 전원(`PIN_LSM6DS3TR_C_POWER`)을 끈 뒤 System OFF 진입. 다시 누르면 재부팅하고 광고를 재개한다.
- LED: 광고 중 파란색, 스트리밍 중 초록색이 2초마다 짧게 깜빡인다. `delay()`를 쓰면 샘플이 빠지므로 비차단 방식으로 구현했다.
- 충전 핀 22는 `INPUT`으로 명시해 기본값(50mA로 알려진 상태)과 같게 두었다. 실제 충전 전류는 여전히 미측정이다.
- 컴파일: `Seeeduino:nrf52:xiaonRF52840Sense`로 성공(exit 0). 최초에는 변수명 `ledOn`이 코어 함수와 충돌해 실패했고(`battery_test`와 같은 문제), `blinkLit`로 바꿔 해결했다.
- 미검증: 업로드, 실제 MTU 협상 결과, 패킷 손실률, 배터리 단독 동작, 소모 전류, System OFF 전류. 수신 쪽 도구(PC 수신 스크립트)도 아직 없다.

## 2026-10-19 — 일시정지/System OFF 분리 및 휴대폰 재연결 측정 화면 추가

- 사용자 결정: 센터 스위치를 1초 미만 누르면 클릭(향후 마우스 클릭용, 일시정지 중이면 재개), 1~3초 누르고 떼면 일시정지, 3초 이상이면 System OFF. 다시 켤 때는 짧게 한 번 누른다. 일시정지와 마우스 클릭을 구분하려고 1초 최소 유지 시간을 둔다. 재연결 지연이 사용감에 영향을 줄 수 있어 일시정지와 System OFF 각각의 재개 시간을 측정하기로 했다.
- 선택 이유: System OFF는 무선까지 꺼져 BLE 연결이 끊기고, 깨어나면 재부팅 → 광고 → 휴대폰 재연결을 거쳐야 한다. 일시정지는 연결은 유지하되 IMU를 끄고 연결 간격을 늘려, 전력을 줄이면서도 즉시 재개를 노린다.
- `firmware/imu_ble_stream/imu_ble_stream.ino` 갱신:
  - 버튼 판정을 뗄 때 하도록 바꿨다. 그래서 3초 누름이 일시정지를 먼저 거치지 않는다. 1초가 지나면 파란 LED를 켜 "지금 떼면 일시정지"를 알린다.
  - 일시정지 시 IMU 가속도·자이로를 power-down(CTRL1_XL/CTRL2_G=0)하고, 연결 간격 100 ms·slave latency 4·감시 시간 4초를 요청하고, loop에 20 ms 휴식을 넣어 CPU를 쉬게 한다. 재개 시 IMU 설정을 다시 적용하고 11.25 ms·latency 0을 요청한다.
  - 상태 characteristic(`b27a2002`, 10바이트)을 추가했다. 일시정지·재개·트리거 후 첫 데이터 송신 이벤트와 기기 시계 기준 경과 시간을 보낸다.
  - 컴파일 성공.
- `android/` 앱에 `ImuMonitorActivity` 추가(메인 화면 7번 버튼):
  - 본딩된 `RingPilot-IMU`에 연결하고 MTU 247을 요청한 뒤 상태·데이터 알림을 구독한다. 끊기면 300 ms 뒤 자동으로 다시 연결한다.
  - 재연결 시점(끊김 → 연결/구독/첫 데이터), 일시정지 재개 결과, 슬롯 간격 기반 누락 샘플 수, 최근 수신율을 화면과 앱 전용 폴더 `imu_reconnect_log.csv`에 기록한다.
  - JDK가 PATH에 없어 Android Studio 동봉 JBR(`JAVA_HOME`)과 저장소 `.tools`의 Gradle/SDK로 `assembleDebug` 성공. 휴대폰 미연결로 설치는 하지 않았다.
- 측정의 한계(설계상): 기기와 휴대폰 시계가 달라 절대 종단 지연은 직접 재지 못한다. 일시정지 재개는 "기기 기준 클릭 뗌 → 첫 데이터 송신"과 "휴대폰 기준 재개 알림 수신 → 결과 수신"을 함께 본다. System OFF는 "기기 기준 부팅 → 첫 데이터 송신"(부트로더 시간 제외)과 "휴대폰 기준 끊김 감지 → 첫 데이터"를 함께 본다. 휴대폰 측 값에는 사용자가 전원을 꺼 둔 시간이 포함되므로, 실제 지연은 기기 측 값 위주로 해석한다.
- 미검증: 업로드, 휴대폰 설치, 실제 측정값, 일시정지 중 전류.

## 2026-10-19 — IMU BLE 1차 실측: 일시정지 동작 확인, 재연결 버그 3건 수정

- 펌웨어(COM10 업로드)와 앱(adb 설치)을 실기기에 올리고 사용자가 일시정지·전원 끄기를 시험했다. 로그: `docs/logs/2026-10-19-imu-ble-reconnect-1.csv`.
- 업로드 직후 LED가 "1번, 2번" 섞여 깜빡인다는 사용자 관찰이 있었다. 원인은 Bluefruit 기본 연결 LED(광고 중 파란 LED 자동 깜빡임)가 상태 LED와 겹친 것으로 판단해 `Bluefruit.autoConnLed(false)`로 끄고 재업로드했다. 수정 후 LED 모양은 아직 사용자 확인 전이다.
- 확인된 것(로그 근거):
  - 연결 시 MTU 247 협상 성공.
  - 일시정지 2회는 보드가 `PAUSED`를 보고했다. LED는 1초 누를 때 파랑 점등, 일시정지 중 청록 깜빡임.
  - 재개 1회: 보드 시계 기준 "클릭 뗌 → 첫 데이터 송신" 93 ms, 휴대폰 기준 재개 알림 수신 → 결과 수신 200 ms.
  - 전원 끄기/켜기 2회 모두 자동 재연결 후 수신이 재개됐다.
- 측정값(표본 1~2회, 참고용): 전원 켜기 후 데이터 재개는 두 번째 회차 약 1.8초(보드 uptime으로 추정). 첫 회차 3.9초는 아래 버그 1로 부풀려졌다.
- 발견한 버그와 수정:
  1. 전원 끄기 시 연결을 끊은 뒤 손을 뗄 때까지 기다리는 동안 라이브러리가 광고를 자동 재시작했다. 그 결과 휴대폰이 0.6초 만에 다시 붙었다가 보드가 꺼지며 MTU 요청이 5초 뒤 실패(status 133)해 재연결이 늦어졌다. → 끄기 전에 `restartOnDisconnect(false)`와 `Advertising.stop()`을 먼저 호출.
  2. 두 번째 재부팅 회차에서 "첫 데이터 송신" 상태 알림이 휴대폰에 도착하지 않아 결과 줄이 빠졌다. 데이터 알림 직후 송신 버퍼가 차서 실패한 것으로 추정한다. → 상태 알림을 4칸 대기열에 두고 실패 시 loop에서 순서대로 재전송.
  3. 앱이 측정 시작 때 이미 켜져 있던 보드의 첫 데이터를 재부팅 결과(`RESULT_boot_reconnect`, 207,696 ms)로 잘못 기록했다. → 끊김 이력이 없으면 `initial_first_data`로 구분.
- 수정본: 펌웨어 컴파일 성공, 앱 빌드·설치 성공. 펌웨어는 보드 USB가 분리돼 아직 재업로드하지 않았다.

  - 누락 샘플 수와 수신율은 화면에만 표시되고 로그 파일에는 남지 않는다.

## 2026-10-20 — 수집용 앱 개편, 원시값 전송, PC 옮기기 도구

- 사용자 요청: 본격적인 데이터 수집을 앞두고 수집하기 편하게 앱을 고친다. 휴대폰 용량 때문에 PC로 옮긴 뒤 휴대폰에서는 지운다. 앱에서 더 쓰지 않을 과거 기능은 제거한다. 접근성 스와이프 서비스는 사용자 선택에 따라 코드만 남기고 화면에서 뺐다(최종 출력 경로로 재사용 예정).
- 펌웨어(`imu_ble_stream`): 센서 원시 int16 값을 그대로 보내도록 바꿨다. 이전에는 mg·0.1 dps로 반올림해 USB 수집 대비 가속도 약 8배, 자이로 약 3배 거친 해상도였다. 패킷 크기는 같다. 환산 계수(0.122 mg/LSB, 0.035 dps/LSB)는 LSM6DS3 라이브러리 `calcAccel`/`calcGyro`에서 확인했다.

## 2026-10-21 — 본 수집 전 수정: 자이로 ±2000 dps, 4초 녹화·1초 대기, NONE 출처 버그

### 목적과 결정

### 변경 내용

- 펌웨어 `imu_ble_stream`: `gyroRange` 1000 → 2000. 자이로 1 LSB = 0.070 dps(데이터시트 70 mdps/LSB, 라이브러리 `calcGyro`의 `gyroRange/125` 계산과 같은 값).
- 앱 `MainActivity`: 자이로 환산 4.375×16/1000, 방향 녹화 400행(4초), 동작 신호 1000 ms. `session_info.txt`에 `gyro_range_dps`와 실제 환산 계수를 기록한다. **펌웨어와 앱은 함께 올려야 한다.** 옛 펌웨어에 새 앱을 쓰면 자이로가 2배로 기록된다.
- `suggest-gesture-completions.js`:
  - 300행 고정 가정을 없앴다. 세션의 `session_info.txt`에서 클립 길이·신호 시각·자이로 범위를 읽고, 없으면 300행/500 ms/±1000 dps로 본다. `early_motion`은 신호 시각 전 동작, `late_completion`은 클립 끝 0.5초 이내, `near_gyro_limit`는 범위의 90%로 일반화했다. `--id-start` 옵션을 추가했다.
  - 시험 중 발견한 문제를 고쳤다. 1%/99% 에너지 지점을 모든 샘플의 누적으로 계산하면, 착용 상태의 정지 잡음(10~30 dps)이 클립 길이만큼 쌓인다. 그래서 4초 클립에서는 시작이 앞당겨지고(거짓 `early_motion`) 완료 시점이 최대 약 0.7초 늦어졌다. 에너지 계산을 동작 기준(평활 자이로가 최고값의 8%, 12~40 dps) 이상인 샘플로 한정했다.
  - 그러자 잡음이 큰 꼬리에서 안정 기준이 느슨해(약 50 dps) 복귀 중에 완료로 판정되는 경우가 드러났다(`raw_right.5`). 안정 판정에 자이로가 동작 기준 미만일 것을 추가했다.
- `export-gesture-windows.js`:
  - NONE 상한을 원본 순서대로 채워 뒤쪽 idle/other가 선택되지 않던 버그를 고쳤다. 출처 종류(동작 클립 배경/idle/other)별로 번갈아 고르고, 각 종류 안에서는 기록별로 번갈아 고른다.

## 2026-10-21 — 무선 데이터 초기 1D-CNN 아키텍처 v1 설계

- 목적: 사용자 요청에 따라 현재 배터리·BLE 데이터용 첫 모델 구조를 구체화한다.

- 구조: 160×6 입력 → Conv1D(16,k5,same,ReLU) → MaxPool(2) → Dropout(0.2) → Conv1D(32,k5,same,ReLU) → MaxPool(2) → Flatten(1280) → Dropout(0.3) → Dense(5,softmax). 클래스 순서는 NONE/UP/DOWN/LEFT/RIGHT. 총 9,493개 파라미터, Conv/Dense 계산량 약 288,000 MAC/회(20 Hz면 5.76M MAC/초, 실측 속도가 아님).
- 선택 이유: 현재 독립 원본이 적으므로 두 층의 작은 기준선으로 시작한다. Flatten에서 시간 위치를 보존하고 중간 Dense는 생략한다. 전체 과거 창만 입력하므로 same padding을 써도 판정 시각 이후 자료는 사용하지 않는다. 마지막 특징 하나만 취하는 얕은 TCN으로 잘못 해석하지 않도록 전체 창 참조를 명시했다.
- 문제/해결: 기존 내보내기 도구의 창 종료 시각이 마지막 샘플보다 10 ms 큰 점을 확인했다. v1은 마지막 실제 샘플 timestamp로 정의하고 향후 데이터 생성/replay 구현 시 맞추도록 기록했다. 도구 코드는 이번에 바꾸지 않았다. 초기 준비 부족·양성 구간 잘림은 별도 표시하고 가짜 앞부분 채우기를 사용하지 않도록 설계했다.
- 검증: `ml/.venv` Python 3.12.15 / TensorFlow 2.21.0에서 모델 생성 및 배치 1, 160행×6축 영 입력 추론 성공. 레이어 크기와 파라미터 9,493개 확인, 출력 (1,5), 유한 값, 합 1.0. MAC 수식 계산과 README/설계 문서의 내부 파일 링크 존재 검사 통과. `git diff --check` 오류 없음(진행기록 줄바꿈 변환 경고 있음).
- 미실행: 새 주석 생성, 분할 적용, 실제 학습, 인식 성능 측정, int8 변환, 펌웨어 통합, 보드 동작/지연/메모리 실측. threshold 0.8, margin 0.2, 2회 연속은 검증에서 조정할 초기 제안값이다.

## 2026-10-25 — BLE v2 계획 외부 검토 반영

- 배경: 사용자가 v2 계획에 대한 검토 의견(외부)을 가져왔다. 지적 6가지를 문서·코드와 대조했다.
- 받아들여 고친 것(`docs/TrainingPlan.md` BLE v2 절·분할 절, `docs/experiments/ble-v2/README.md`):
  - C − S를 "자세를 학습에 넣지 않았을 때 잃는 성능"으로 단정하던 문구를 "새 자세·세션 일반화 문제의 단서"로 바꿨다. 세션 하나가 자세 하나라 수집 시각·착용 상태가 함께 바뀌고, 평가 구성(S는 P5뿐, C는 5세션 혼합, 배경 80/100초)도 다르기 때문이다.
  - "5 seed 같은 부호 + 보정 seed 범위보다 크면 차이 있음" 판정 규칙을 삭제하고 기술 보고(크기, 5 seed 중 몇 개에서 C > S인지, 세션별 흩어짐)로 바꿨다. seed 반복은 학습 무작위성만 보여 주고 평가 세션 변동은 못 보여 준다.
  - S 회전(P1~P5 각각 빼기)을 선택에서 기본으로 올렸다. 학습은 P1~P4 추가분 100회, 전체 155회다.
  - "데이터 처리 순서(누수 방지)"를 명시했다. 원본 분할 → 창 생성 → fold 학습 부분만으로 정규화 → NONE 추출은 학습에만.
  - "발행·채점 protocol"을 명시했다. 판정 시각, 발행 시각, 원본별 초기화, e는 발행에 쓰지 않음, 분류 우선순위, e > 3490 ms(허용 구간이 클립 끝에서 잘림) 원본 표시. 현재 `ml/baseline.py`의 `issue_events()`·`classify_events()` 동작과 대조해 일치함을 확인했다.
  - E 후보에 1·5를 넣었다({1, 5, 10, 20, 30, 40, 60}). E 선택 점수는 seed마다 fold 예측을 합친 (정검출 − 방향 원본 미매칭) ÷ 검증 방향 원본 수로 정했고, 배경 오발행은 점수에서 빼고 따로 보고한다. 배경이 짧아 가중치를 정할 근거가 없다는 판단이다. 방식별로 E가 다를 수 있으며, 그 경우 "같은 선택 원칙"을 적용한 비교라고 쓴다.
  - 보고 표를 분모별로 정리했다. 정검출/원본 수, 미매칭은 원시 개수와 원본당, 배경은 원시 개수·실제 판정 구간·분당, 지연은 정검출률과 함께.
- 이미 계획에 있던 것: fold마다 정규화 재계산, NONE 추출은 학습에만, 보정 학습 횟수(S 20회·C 25회, 한 번 60 epoch까지 학습하며 중간 시점 평가). 검토자가 본 225회는 채팅에서 말한 개별 학습 기준 수치였다.
- 검증: 내부 링크·앵커 스크립트 확인. 문서만 수정했고 코드·학습은 하지 않았다.

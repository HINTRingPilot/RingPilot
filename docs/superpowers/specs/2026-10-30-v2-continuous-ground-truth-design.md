# 연속 사용 평가의 정답 표시 설계(Task 8)

작성: 2026-10-30. 상태: **설계 초안, 사용자 검토 전.** 관련 계획: `docs/superpowers/plans/2026-10-29-v2-next-steps.md` Task 8. 남은 일 목록: `docs/TODO.md`.

## 1. 목적과 범위

지금 정검출 97.11%는 클립 단위 교차검증 값이다. 클립마다 발행 상태를 초기화하고, 클립 시작 0~890 ms의 정지 구간으로 영점을 잡는다. 실제로 반지를 계속 끼고 쓰는 상황과 다르다. Task 8은 연속 녹화로 다음을 확인한다.

1. **연속 동작 정확도**: 정검출, 놓침, 잘못된 방향. 빠른 다음 동작이 불응기 규칙(R1) 때문에 막히는지(R0와 비교).
2. **배경 오발행**: 제스처 없이 일상 동작을 할 때 시간당 오발행 수.
3. **온라인 영점 안정성**: "직전 정지 구간" 방식(`ml/v2_stream.py` `still_estimates`)으로 잡은 영점이 실제 사용에서 버티는지.
4. **정답 자체의 신뢰도**: 지금 학습·평가의 정답 시각 r도 신호에서 자동으로 정한 값이다. 일부를 영상으로 대조한다(선택).

범위 밖: 보드 추론(Task 7a), 실제 스와이프를 하는 제어 모드 앱, 모델 학습 변경.

**이 설계를 녹화 전에 정하는 이유:** 연속 녹화에서 "언제 어떤 방향을 의도했는지"는 녹화 뒤에 복원하기 어렵다. 같은 동작을 모델과 사후 검출기가 똑같이 착각하면 오류가 드러나지 않는다. 그래서 의도는 녹화하는 순간 앱이 기록하고, 정확한 시각만 사후에 신호에서 찾는다.

## 2. 정답 구조(3단계)

| 단계 | 무엇을 | 어떻게 | 누가 |
|---|---|---|---|
| ① 의도 | 어떤 방향(들)을 대략 언제 | 앱의 **연속 안내 모드**가 음성으로 안내하고, 안내마다 시각과 그 순간 받은 샘플 번호를 **안내 기록(cue log)**에 남긴다 | 앱(녹화 중 자동) |
| ② 정확한 시각 | 가는 피크·끝점·복귀 피크·r | 안내 시각 기준 구간을 잘라 **기존 자동 라벨 규칙**으로 찾는다. 클립 평가와 같은 정답 정의 | PC 도구(자동) |
| ③ 검토 | 애매한 것만 | 자동 표시(flag)된 경우만 그래프로 보고 포함·제외·수정, 사유 기록 | 사람 |
| (선택) 영상 감사 | 자동 r이 실제 동작과 맞는지 | 일부 세션을 휴대폰 영상과 함께 녹화해 대조 | 사람 |

## 3. 시각 맞추기

가장 중요한 기술 문제다.

- 센서 시각: CSV `timestamp` = (보드 슬롯 번호 − 기록 첫 슬롯) × 10 ms. 보드가 10 ms 슬롯 번호를 붙여 보내고(`firmware/imu_ble_stream`), 빠진 슬롯은 연속 기록에서 시각 간격으로 남는다(`MainActivity.acceptSamples`).
- 안내 시각: 휴대폰 `SystemClock.elapsedRealtime()`(ms).
- 연결 방법: 안내하는 순간 앱이 아는 **마지막으로 받은 슬롯 번호**와 **그 패킷이 도착한 시각**을 함께 기록한다. 안내의 센서 시각 추정 = (마지막 슬롯 − 첫 슬롯) × 10 + (안내 시각 − 마지막 패킷 도착 시각).
- 오차: BLE 패킷 묶음·전송 지연(수십 ms 예상), 소리 출력 지연, 사람 반응 시간(수백 ms, 매번 다름). 정확한 r은 신호에서 찾으므로, 안내 시각 오차는 "어디서 찾을지"(검색 구간)에만 영향을 준다. 수십 ms 오차는 허용된다.
- 확인: 5분 시험 녹화에서 안내 → 움직임 시작까지의 지연 분포를 본다(예상 0.3~1.0 s). 모든 안내 뒤 움직임이 검색 구간 안에 들어오면 정렬이 맞는 것이다.

## 4. 녹화 구성(초안, 기본값은 결정 필요)

| 블록 | 내용 | 안내 | 보는 것 | 제안 분량(세션당) |
|---|---|---|---|---|
| A 단일 방향 | 4방향 무작위 | 방향 하나, 다음 안내까지 3~5 s(무작위) | 클립 평가와 비교되는 기준 정확도, 연속 상태·온라인 영점 영향 | 방향별 8회(32회) |
| B 빠른 쌍 | 두 동작을 최대한 빠르게(예: "위 아래", "오른쪽 왼쪽", "위 위") | 한 번 안내에 방향 두 개 | **R1이 빠른 다음 정상 명령을 막는지**, 연속 동작에서의 반대 방향 재발행 | 쌍 16회(반대 8, 같은 방향 4, 직각 4) |
| C 편한 연속 | 1.0~1.5 s 간격으로 이어지는 단일 안내 | 방향 하나씩 짧은 간격 | 편한 속도의 연속 조작 | 16회 |
| D 일상 동작 | 제스처 없이 타이핑·마우스, 걷기, 말하며 손짓, 컵 들기, 휴대폰 쓰기 | 블록 시작·끝만 안내 | 시간당 오발행 | 동작별 5~10분 |
| E 정지 | 손을 편히 두고 가만히 | 시작·끝만 | 영점 기준 구간, 정지 중 오발행 | 2분 |

- 세션 메모에 자세(앉기·서기)와 손목 방향을 적는다. 세션은 서로 다른 자세·날짜로 2개 이상을 제안한다.
- 블록 D 중 실수로 제스처를 했으면 앱의 "방금 실수" 버튼으로 표시한다(그 시각 앞뒤 3 s는 배경 채점에서 뺀다).
- 피로를 줄이려고 블록 사이에 1~2분 쉰다. 쉬는 시간은 기록을 멈추지 않고 블록 E처럼 정지로 표시해도 된다.

## 5. 앱 변경 설계(연속 안내 모드 + 안내 기록)

원칙: **기존 안내 수집·연속 기록 동작은 바꾸지 않는다. 펌웨어는 바꾸지 않는다(`imu_ble_stream` 그대로).** 새 모드만 더한다.

- **화면:** "연속 안내 수집" 버튼 하나와 블록 선택(A~E)을 더한다. 진행 중에는 현재 블록·남은 안내 수를 보여 주고, "방금 실수"(블록 D)와 "방금 안내 취소"(A~C에서 동작을 못 했을 때) 버튼을 둔다.
- **기록:** 블록 하나를 연속 기록 하나로 저장한다. 기존 연속 기록과 같은 방식(`startCapture(label, 0, ...)`, 64 KB마다 덧붙이기, 공백은 시각 간격)이고, 이름만 `guided_<블록>.<번호>.csv`로 한다. 사이드카(`.capture.json`)도 그대로 생긴다.
- **안내 기록 파일:** `guided_<블록>.<번호>.cues.csv`. 안내·표시가 생길 때마다 한 줄을 덧붙인다(기존 `fileWriter` 단일 스레드 사용, 순서 보장).

  | 열 | 뜻 |
  |---|---|
  | `cue_id` | 기록 안 일련번호 |
  | `kind` | `cue`(방향 안내), `block_start`, `block_end`, `void`(직전 안내 취소), `mistake`(블록 D 실수 표시) |
  | `intended` | `UP`·`DOWN`·`LEFT`·`RIGHT`, 쌍이면 `UP+DOWN`, 그 밖은 빈칸 |
  | `target_cue_id` | `void`일 때 취소한 안내 번호 |
  | `tone_elapsed_ms` | 동작 신호음(삐빅)을 낸 휴대폰 시각 |
  | `last_slot` | 그 순간까지 받은 마지막 보드 슬롯 |
  | `last_arrival_elapsed_ms` | 그 슬롯이 든 패킷의 도착 시각 |
  | `first_slot` | 이 기록의 첫 슬롯(시각 0) |
  | `est_data_ms` | 3절 식으로 계산한 안내의 센서 시각 |

- **안내 순서:** 기존 안내 수집의 단계 예약(`postGuide`, `guideGeneration`)을 그대로 쓴다. 음성(방향) → 짧은 대기 → 동작 신호음 순서이고, 신호음 시각을 `tone_elapsed_ms`로 쓴다. 블록 안 순서는 녹화 전에 섞어 정하고, 그 순서도 기록 첫 줄(`block_start`)에 남긴다.
- **샘플 정보 공유:** `acceptSamples`가 이미 `captureLock` 안에서 슬롯과 도착 시각을 다룬다. 마지막 슬롯·도착 시각을 그 안에서 저장하고, 안내 기록이 같은 잠금으로 읽는다.
- **끊김 처리:** 링 연결이 끊기면 안내를 멈추고(기존과 같음), 다시 이어지면 `block_start`를 새로 쓰고 이어 간다. 끊김 구간에 걸친 안내는 PC 도구가 제외한다.
- **PC로 옮기기:** `tools/pull-phone-sessions.js`가 새 파일 이름(`guided_*.csv`, `*.cues.csv`)도 가져오는지 확인하고, 아니면 고친다.
- **새 코드 단위:** `CueLog`(안내 기록 파일 쓰기, `CaptureSidecar`처럼 작은 클래스)와 `GuidedStream`(블록별 안내 순서·시각 생성, 화면과 분리해 단위 시험 가능). `MainActivity`(798줄)에는 버튼과 연결만 더한다.

## 6. 정답 만들기(PC, 녹화 뒤)

1. 안내 기록을 읽어 `void`된 안내를 빼고, 각 안내의 센서 시각을 계산한다.
2. 안내마다 **안내 1 s 전 ~ 3 s 뒤**(쌍은 4 s 뒤)를 잘라 기존 클립과 같은 모양(앞 1 s 정지, 이후 동작)으로 만든다. 기존 자동 라벨 규칙(`tools/suggest-gesture-completions.js`, `tools/derive-return-labels.js`의 주축 자이로·가는 피크·끝점·복귀 피크·r)을 그대로 적용한다. 정답 정의가 클립 평가와 같아진다. 쌍은 구간 안에서 동작 두 개를 차례로 찾는다.
3. 자동 표시(flag): 움직임 없음, 동작이 예상보다 많음, 검출 방향 ≠ 안내 방향, 안내 뒤 0.2 s 안(안내 전에 움직임) 또는 2.5 s 뒤(늦음), 쌍에서 하나만 검출, 구간 안 데이터 공백.
4. 표시된 것만 사람이 그래프로 보고 포함·제외·수정한다. 사유를 남긴다(데이터 큐레이션 기록과 같은 방식).
5. 결과 파일: 녹화마다 `<녹화>.truth.json`. 동작 목록(`cue_id`, 의도 방향, 가는 피크·끝점·복귀 피크·r, `auto`/`reviewed`/`excluded`, 사유)과 배경 구간 목록(시작·끝, 블록, 실수 표시로 뺀 구간).

## 7. 채점 정의(구현은 다음 계획, 기준 수치는 녹화 전에 고정)

- 방향 동작: [끝점, r+300 ms] 안에 의도 방향 발행 → 정답, 같은 구간에 다른 방향 → 잘못된 방향, 없음 → 놓침. 클립 채점(`extreme_window`)과 같다.
- 빠른 쌍: 두 번째 동작이 놓침이고 그 시각이 첫 발행 뒤 불응기 안이면 "규칙에 막힘"으로 따로 센다.
- 동작 구간 밖 발행: 오발행. 블록 D·E는 시간당 오발행으로 낸다.
- 발행 상태는 녹화 하나 안에서 끊지 않는다(`v2_stream.replay`). R0·R1을 함께 채점한다.
- 영점: 온라인 정지 구간 방식과 비교용 기준(블록 시작의 정지 구간 값을 고정) 두 가지로 채점해 영점 영향만 따로 본다.

## 8. 위험과 대응

| 위험 | 대응 |
|---|---|
| 안내를 듣고 하는 동작은 실제 사용보다 반응적이다 | 정확도는 안내 블록으로, 오발행은 안내 없는 블록 D로 나눠 잰다. 결과에 이 한계를 적는다 |
| 사람 반응 시간이 들쭉날쭉하다 | 검색 구간을 넓게(0.2~3 s) 두고 벗어나면 flag |
| 자동 라벨 오류가 정답에 그대로 들어간다 | flag 검토, 선택적 영상 감사 |
| BLE 끊김 | 공백을 시각 간격으로 남기고, 공백에 걸친 안내는 제외 |
| 피로로 동작이 약해진다 | 블록 사이 휴식. 약한 동작은 2026-10-28 결정대로 평가에 포함하되 기존 기준(방향 중앙값 0.6배)으로 따로도 집계 |

## 9. 결정이 필요한 것(사용자)

1. 4절 블록 구성과 분량(제안 기본값으로 갈지).
2. 영상 감사를 할지(한다면 세션 1개, 블록 A·B만 제안).
3. 블록 B 쌍 구성(반대 방향 위주로 갈지).
4. 채점 기준 수치(예: 연속 정검출 목표, 시간당 오발행 목표)는 채점 계획을 쓸 때 녹화 전에 정한다. 현재 제안 목표는 시간당 오발행 1회 이하다.
